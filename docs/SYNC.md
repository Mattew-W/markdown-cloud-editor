## 1. 编辑会话字段

每个文档编辑会话维护以下字段。**这些字段名是契约**，`sync.js` 与 `drafts.js` 必须一致。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `doc_id` | string (UUID) | 当前编辑的文档 ID |
| `edit_session_id` | string (UUID) | 本次打开的会话 ID。**每次打开文档必新生成**，切换文档必重新生成 |
| `base_version` | integer | 当前云端基准版本。**只能来自服务端响应**，不得自行 +1 |
| `local_revision` | integer | 本地修订号。**每次输入 +1**（标题修改与正文修改**同样计入**） |
| `acked_revision` | integer | 已获服务端确认的 `local_revision` |
| 发送中快照 | object | 已发出但尚未收到响应的 `{ revision, title, content, base_version }` |

### 1.1 `edit_session_id` 的生成与作用域

```
crypto.randomUUID()
```

| 规则 | 说明 |
| --- | --- |
| 生成时机 | **每次打开文档时** |
| 作用域 | **一次文档打开会话** |
| 切换文档 | **必须重新生成**，不跨文档复用 |
| 不跨 | **不跨用户复用、不跨标签页复用** |

> **为什么需要它**：草稿键含 `edit_session_id`（见 §8.2）。若会话 ID 复用，同一标签页两次打开同一文档会写进同一草稿槽位，导致"上次会话的旧草稿"与"本次会话的新草稿"互相覆盖，且无法在恢复时区分。验收项 T09「多窗口与删除冲突：草稿分离」依赖此字段。

### 1.2 `local_revision` 的递增规则

| 操作 | `local_revision` |
| --- | --- |
| 正文输入（`input` 事件） | **+1** |
| **标题修改** | **+1**（标题与正文同等对待） |
| 仅选中/移动光标 | **不变** |
| 预览重绘 | **不变** |
| 保存成功 | **不变**（推进 `acked_revision`，不改 `local_revision`） |

> **标题修改必须计入**，否则标题改动不受自动保存保护。验收项 T14 涉及标题边界。

### 1.3 协调器的唯一性

**每个标签页按 `(user_id, doc_id)` 保留唯一保存协调器。** 切换编辑视图**不会**创建另一套并行保存通道。

A → B → A 时，**复用 A 的协调器**（见 §7.2）。

## 2. 调度参数（全部为冻结常量）

| 参数 | 值 | 触发条件 |
| --- | --- | --- |
| **防抖（debounce）** | **1.5 秒** | 停止输入后触发保存 |
| **最大等待（max-wait）** | **5 秒** | 持续输入满 5 秒尝试保存一次 |
| **手动保存** | 立即 | `Ctrl+S` / `Cmd+S` |
| **在途请求上限** | **同一文档最多 1 个** | 有请求在途时**合并**待保存修改，**不排队** |
| **请求超时** | **10 秒** | `AbortController` |

### 2.1 防抖与 max-wait 的关系

两条规则**并行生效**，任一满足即触发：

```
t=0.0s  输入开始
        ↓ 持续输入
t=1.5s  防抖计时重置（因为仍在输入）
        ↓ 继续输入
t=5.0s  max-wait 触发 → 发起保存【即使仍在输入】
        ↓ 继续输入
t=5.6s  1.5 秒无输入 → 防抖触发 → 若有在途请求则合并
```

**为什么需要 max-wait**：只有防抖的话，持续打字 30 秒就一次都保存不上，中途崩溃会丢失全部内容。max-wait 保证长会话也定期落盘。

### 2.2 在途请求上限 = 1

**同一文档同时最多一个 `PUT` 在途。**

| 情况 | 处理 |
| --- | --- |
| 无在途请求 + 调度触发 | 立即发送当前最新快照 |
| **有在途请求 + 又有新输入** | **不发送**。记下"待保存"标记；当前请求完成后**发送最新快照** |
| 有在途请求 + 又触发调度 | **不发送**（同上） |

> **排队会积压**：若允许 N 个在途，用户快速输入会产生一串延迟到达的请求，后到的旧快照会覆盖先到的新快照，且服务端版本号会被快速推高。**合并为"完成后发最新"是唯一正确做法。**

### 2.3 5 秒是调度目标，不是落库保证

**5 秒是正常前台运行时的调度目标，不是慢网、后台标签页或离线场景的落库保证。** 不得在任何文案中承诺"5 秒内一定保存成功"。

### 2.4 前端不重建编辑节点（验收项 T13）

| 规则 | 说明 |
| --- | --- |
| 自动保存**不得**重建 `<textarea>` | 否则焦点丢失、光标跳位、IME 组合输入被打断 |
| 保存响应**不得**写回编辑框 | 见 §4.2 |
| **编辑内容由编辑器当前状态持有** | 保存流程只读，不写 |

> 中文输入法（IME）组合输入期间会触发一连串 `input` 事件。自动保存若在中途把内容写回输入框，会打断用户的拼音组合。**T13「自动保存不重建编辑节点，不干扰选区与组合输入」直接测这一点。**

## 3. 状态机

### 3.1 状态与退出条件

| 状态 | 含义 | 退出条件 |
| --- | --- | --- |
| `synced` | 当前修订已获服务端确认 | 用户继续编辑 → `dirty` |
| `dirty` | 存在未确认修改 | 调度发起保存 → `saving` |
| `saving` | 一个快照正在提交 | 收到确认 → `synced`；出现错误 → 见 §6 |
| `retry_wait` | 网络或服务异常，等待核对与重试 | 网络恢复 / 退避结束 / 手动重试 |
| `auth_required` | 凭据失效 | 同一账号重新认证 |
| `conflict` | 服务端出现不同版本 | 用户完成冲突处理 |
| `invalid` | 标题、正文或请求不符合限制 | 用户修正输入 |

### 3.2 状态转移表

| 当前状态 | 事件 | 下一状态 |
| --- | --- | --- |
| `synced` | 用户输入 | `dirty` |
| `synced` | 切换文档 | 草稿落盘后按 §7 处理 |
| `dirty` | 防抖 / max-wait / Ctrl+S 触发 | `saving` |
| `dirty` | 401 | `auth_required` |
| `dirty` | 400 / 413 | `invalid` |
| `dirty` | 409 | `conflict` |
| `saving` | 200 | 见 §4（确认规则） |
| `saving` | 401 | `auth_required` |
| `saving` | 409 | `conflict` |
| `saving` | 400 / 413 | `invalid` |
| `saving` | 网络错误 / 超时 / 5xx | `retry_wait`（按 §6 四分支核对） |
| `saving` | 429 | `retry_wait`，**等待 `Retry-After`** |
| `retry_wait` | 退避到期 / 网络恢复 / 手动重试 | `saving`（发最新快照） |
| `auth_required` | 重新登录成功 | 重新进入 §1 初始化 |
| `conflict` | 用户完成冲突处理 | 按用户选择 |
| `invalid` | 用户修正输入 | `dirty` |

## 4. 保存确认规则

> ### 4.1 只确认发送时的 `local_revision`
>
> 保存成功**只确认发送时的 `local_revision`**。
>
> ```
> 发送快照时：local_revision = 7, base_version = 3
> 请求在途期间用户又输入：local_revision = 12
> 响应返回（确认 revision 7）：acked_revision = 7
> 结果：acked_revision (7) < local_revision (12) → 仍是 dirty，继续保存
> ```
>
> 此时 `base_version` 应更新为**响应中的 `version`**，但**状态不得变为 `synced`**。

### 4.2 只有确认版本覆盖当前修订才显示"已同步"

**判定条件（三个同时成立）**：

| # | 条件 |
| --- | --- |
| 1 | `acked_revision >= local_revision` |
| 2 | 服务端返回的 `version` 已被采纳为新的 `base_version` |
| 3 | 不存在 `conflict` / `invalid` 状态 |

**三个条件中任何一个不成立，状态栏就不得显示"已同步"。**

### 4.3 响应不得覆盖编辑器内容

| 规则 | 说明 |
| --- | --- |
| 保存响应中的 `content` **不代表**编辑器当前内容 | 它是**发送时快照**的落库结果 |
| **禁止**用响应 `content` 写回 `<textarea>` | 会丢失请求在途期间的输入，并可能打断 IME |
| `base_version` **必须**取自响应的 `version` | **不得**自行 `+1` |
| **不得**用响应 `title` 写回标题输入框 | 同上 |

### 4.4 文案禁令

> ### ⚠ 本节为强约束，违反即返工
>
> **本地备份成功不能显示成云端保存成功。**（规范 §08:349）
>
> | 禁止的文案 | 出现场景 | 为什么禁止 |
> | --- | --- | --- |
> | `"保存成功"`（无前缀） | **本地草稿**写入成功时 | 用户会以为内容已上云，实际只存于本机 |
> | `"已同步"` | 仅本地草稿写入成功、`base_version` 未推进时 | 同上 |
> | `"已保存"` | 同上 | "保存"二字的语义歧义无法靠上下文消解 |
> | `"✅保存成功，保存时间：…"` | 任何本地草稿写入 | **M6 W1 交件正是这句**（`drafts.js` 审核记录 §5.2），W2 第一条必须纠正 |
>
> **正确做法**：本地草稿成功 → 显示 `"已在本地备份"`（或同类措辞），且**不改变** `synced` / `dirty` 判定（见 §9）。
>
> 云端保存成功 → 只有在 §4.2 三个条件全部成立时才显示 `"已同步"`。

**这条禁令的实质**：用户对"我的内容安全吗"的判断完全依赖状态栏文案。把本地备份说成云端保存，会让用户在没真正上云的情况下关闭浏览器并丢失内容。**这不是措辞洁癖，是数据安全问题。**

## 5. HTTP 错误码的状态映射

| 状态码 | `error.code` | 进入状态 | 行为 |
| --- | --- | --- | --- |
| 200 / 201 | — | 按 §4 判定 | 推进 `acked_revision` 与 `base_version` |
| 401 | `UNAUTHORIZED` | `auth_required` | **暂停重试。** 等用户重新认证 |
| 400 | `BAD_REQUEST` | `invalid` | **暂停自动重试**，交用户修正 |
| 404 | `NOT_FOUND` | 见 §6 分支 ④ | 见 §6 |
| 409 | `VERSION_CONFLICT` | `conflict` | **暂停自动写入。** 交用户处理 |
| 413 | `PAYLOAD_TOO_LARGE` | `invalid` | **暂停自动重试**，交用户修正 |
| 429 | `RATE_LIMITED` | `retry_wait` | **遵循响应头 `Retry-After`** |
| 5xx | `INTERNAL_ERROR` | `retry_wait` | 按 §6「结果未知」核对 |

**"暂停重试"与"暂停自动写入"的区别**：

- **暂停自动重试**（400 / 413）：重发同一个请求不会有不同结果，必须等输入改变。
- **暂停自动写入**（409）：在用户明确选择之前，**不得向该文档发起任何写请求**。绕过冲突的唯一合法途径是用户显式决策。

## 6. 超时与「结果未知」四分支

### 6.1 为什么"结果未知"

**`AbortController` 取消等待并不证明数据库已回滚。** 服务端可能已经提交了本次写入，只是响应在网络上丢失了。

网络错误、超时、以及**可能已提交的 5xx**，一律按「结果未知」处理：**保留发送快照，读取云端记录核对。**

> **`navigator.onLine` 不能作为成功证据。** `navigator.onLine` 与 `online` 事件**只用于提示与触发尝试**。浏览器报告"在线"完全不代表请求到达了服务器。把它当成功证据会造成"显示已同步但数据没上去"。

### 6.2 四分支判定

进入 `retry_wait` 后，读取云端记录（[`API.md`](API.md) §7 `GET /documents/{id}`），然后：

| 分支 | 云端标题与正文 | 云端版本 | 处置 |
| --- | --- | --- | --- |
| **① 云端与快照相同** | **完全相同** | 任意 | **确认该快照已持久化**，采纳读取到的版本。若本地又有新编辑，**继续保持 `dirty`** |
| **② 云端版本仍等于快照 `base_version`** | 不同或相同均可 | `== snapshot.base_version` | 用**原 `expected_version`** 重试 |
| **③ 版本已变且内容不同** | **不同** | `!= snapshot.base_version` | 进入 **`conflict`**。**禁止自动套用新版本覆盖云端** |
| **④ 读取返回 404** | — | — | **保留本地内容**，提示云端文档已不可用，**允许另存为新文档** |

### 6.3 分支 ② 的正确性论证

分支 ② 为什么可以安全地用原 `expected_version` 重试？

因为**服务端不知道我们超时了**。若它真的提交了，版本已 +1，分支 ② 的前提（版本仍等于 `base_version`）就不成立，会落入分支 ① 或 ③。所以**只有真正未提交时才会走到分支 ②**，此时用原 `expected_version` 重试是正确的。

**更严格地说**：GET 与重试之间仍可能发生新的写入。但那个写入会让重试的 `version` 条件失败，返回 `VERSION_CONFLICT`，进入 `conflict`。**原子版本条件（见 `docs/DATABASE.md` §6）保证这里的正确性不依赖客户端时序。**

### 6.4 分支 ④ 的处置

- **保留本地内容**，不清空编辑器
- 提示"云端文档已不可用"
- **允许另存为新文档**
- **禁止**自动重建云端占位文档

### 6.5 读取也失败时

**继续保持未确认状态**（不进入 `synced`），按 §7.3 的退避表重试读取。

## 7. 退避与重试

### 7.1 退避表

| 次数 | 等待基数 |
| --- | --- |
| 1 | **1 秒** |
| 2 | **2 秒** |
| 3 | **4 秒** |
| 4 | **8 秒** |
| 5 | **16 秒** |
| 6 及以后 | **30 秒**（上限） |

**每个实际等待时间 = 基数 + 随机扰动。**

**随机扰动的作用**：避免多个标签页同时失败后形成同步的请求浪峰（惊群效应）。扰动幅度应是小幅的，不得大到破坏上限语义。

### 7.2 特殊状态的重试策略

| 情形 | 策略 |
| --- | --- |
| 401 | **暂停重试。** 等用户重新认证 |
| 429 | **遵循响应头 `Retry-After`**，不用退避表 |
| 400 / 413 | **暂停自动重试。** 等用户修正 |
| 409 | **暂停自动写入。** 等用户决策 |
| 网络恢复 / `online` 事件 | **可以**触发一次尝试（作为提前唤醒，不是成功证据） |
| 手动重试按钮 | **可以**立即触发 |

### 7.3 测试要求

退避与防抖的单元测试**必须使用可控时钟**（注入 fake timers），模拟防抖、最大等待和重试，**避免依赖真实长时间等待**。真实等待会让测试慢到无法在 CI 中运行。

## 8. 文档切换

### 8.1 切换文档的标准流程

```
1. 先保存本地草稿（草稿优先于云端保存）
2. 生成新的 edit_session_id
3. 建立新编辑会话
4. 读取云端文档 → 判定恢复分支（§9.3）
5. 如有遗留草稿 → 提示用户选择
```

> **顺序不可调换。** 必须"先保存本地草稿，再建立新编辑会话"。反过来会在切换瞬间丢掉未落盘的输入。

### 8.2 旧响应的隔离规则

**旧响应只能确认原快照并更新所属文档的协调器**，不能：

| 禁止行为 | 后果 |
| --- | --- |
| 直接更新另一编辑会话的**状态栏** | 用户看到错误的保存状态 |
| 直接更新另一编辑会话的**编辑框** | A 的内容污染 B（验收项 T06） |

**实现要求**：每个响应在处理时必须先校验 `response_doc_id === current_doc_id`。不匹配则**只更新对应协调器的内部状态，不触碰当前 UI**。

> 这是验收项 **T06「A 文档切换到 B：A 的旧响应不污染 B 的内容、版本和状态」** 的直接实现点。

### 8.3 未确认修改的处理

**旧文档仍有未确认修改时保留草稿，不静默丢弃。** 切换前必须已按 §8.1 落盘。

### 8.4 A → B → A 的返回流程

```
若 A 的旧请求仍在途或结果未知：
  → 先等待核对完成（按 §6 四分支）
  → 再建立当前编辑会话的云端写入基准（base_version）
  
等待期间：
  ✓ 可以展示 A 的草稿
  ✗ 不得另开保存请求
```

**不得在等待期间用旧的 `base_version` 发起新写入。** 等待的目的是确定服务端真实状态，绕过它就等于放弃了冲突检测。

**不同浏览器标签页仍由服务端 `version` 条件协调。** 客户端协调器只解决单标签页内的并发。

## 9. 本地草稿机制

### 9.1 定位

| 项 | 说明 |
| --- | --- |
| 存储 | **`localStorage`**（首版） |
| 访问方 | **统一由 `drafts.js` 访问。** 其他模块**不得**直接读写 |
| 写入时机 | 约 **250 毫秒合并写入**，切换文档前同步尝试刷新 |
| 权威性 | **草稿是兜底，自动保存是主路径。** 草稿写入成功**不得**改变 `synced` / `dirty` 判定 |

> `sync.js` / `editor.js` / `app.js` **一律不得**直接调用 `localStorage`。这是防止"两份语义不同的副本"的唯一手段（`docs/ARCHITECTURE.md` §3）。

### 9.2 草稿键

```
markdown-editor:draft:{userId}:{docId}:{sessionId}
```

| 段 | 值 | 说明 |
| --- | --- | --- |
| 前缀 | `markdown-editor:draft:` | 全应用统一 |
| `userId` | 当前用户 UUID | **防止跨账号草稿互相可见** |
| `docId` | 文档 UUID | |
| `sessionId` | `edit_session_id` | **防止同账号多标签页互相覆盖** |

**各段必须做分隔符安全编码**，避免 UUID 之外的字符破坏键结构。提供 `parseDraftKey()` 供枚举使用。完整规则见 [`INTERFACES.md`](INTERFACES.md) §2（C2）。

> **为什么必须含 `user_id`**：不含则共享设备上切换账号后，后一个账号能读到前一个账号的草稿内容——**隐私事故**。M6 W1 交件使用单一固定键，正是这个缺陷。

### 9.3 草稿记录

```json
{
  "user_id": "6f1a3c2e-8b5d-4a71-9f0e-2d3c4b5a6e7f",
  "doc_id": "b2e9d4f1-0c3a-4e5b-8d7a-1f2e3d4c5b6a",
  "edit_session_id": "c3d5e7a9-1b2f-4c8d-9e0a-3f4c5d6e7f8a",
  "base_version": 3,
  "title": "课程笔记",
  "content": "# 课程笔记\n\n第一段落。",
  "local_revision": 7,
  "recorded_at": "2026-10-20T08:45:12Z"
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `user_id` | 是 | 与键中的段一致 |
| `doc_id` | 是 | |
| `edit_session_id` | 是 | |
| `base_version` | 是 | **恢复判定的核心依据** |
| `title` | 是 | **标题改动也必须有草稿保护** |
| `content` | 是 | 允许空串 |
| `local_revision` | 是 | 清理核对用 |
| `recorded_at` | 是 | **ISO 8601 UTC 字符串，不是 `Date.now()` 数字** |

> **`recorded_at` 只用于展示**，恢复判断**以版本和内容为依据**。

> **M6 W1 交件的缺陷**：只存 `{content, savedAt}`，缺 `base_version` / `title` / `local_revision` / `user_id` / `doc_id` / `edit_session_id`。**缺 `base_version` 使冲突判定无法实现；缺 `title` 使标题改动完全没有草稿保护。**

### 9.4 250 毫秒合并写入

**约 250 毫秒**内的连续输入合并为一次写入。

**理由**：每次输入都写 `localStorage` 会造成明显的主线程卡顿（同步 API + JSON 序列化）；完全不合并则会在浏览器崩溃时丢失最后一段。

**切换文档前必须同步尝试刷新**（绕过 250 毫秒合并，立即写一次）。

### 9.5 遗留草稿枚举

重新打开文档时，**枚举该账号该文档的遗留草稿**，显示版本与时间，**供用户选择恢复**。

**不得自动恢复。** 自动恢复可能把过期内容静默覆盖用户的当前编辑。

### 9.6 清理草稿的三重核对

> **清理草稿前必须核对会话、修订号和内容，不能删除保存期间刚产生的新修改。**（规范 §08:376）

| # | 核对项 | 不一致时的处置 |
| --- | --- | --- |
| 1 | **`edit_session_id` 相等？** | **拒绝删除** |
| 2 | **`local_revision` 相等？** | **拒绝删除**（期间有新输入） |
| 3 | **`content`（或完整记录）相等？** | **拒绝删除** |

**三项全部相等才允许删除。** 任一不等即拒绝。

> **这是最容易被漏掉的一条。** M6 W1 交件直接 `removeItem` + 清空编辑器——在保存进行中点击"清除草稿"，会**抹掉刚产生的新修改**。规范 §08:376 明令禁止。

**"选中遗留草稿"时的额外规则**：复制到当前编辑会话，**保留原记录直至用户确认处置**，避免误删其他活动窗口的草稿。

### 9.7 恢复的三分支

| 分支 | 条件 | 处置 |
| --- | --- | --- |
| **① 内容与云端相同** | 草稿 `content` 与云端 `content` **完全相同** | **可确认**，直接采用云端，清除草稿 |
| **② 云端版本等于草稿 `base_version`** | 云端 `version === draft.base_version` | **用户确认后**继续保存 |
| **③ 云端版本不同且内容不同** | `cloud.version !== draft.base_version` **且** `content !== draft.content` | **进入 `conflict`** |

> **⚠ 严禁的行为：禁止为旧草稿直接替换成最新 `base_version` 后自动提交。**
>
> 这等于用客户端的乐观假设覆盖服务端状态，是"静默丢数据"的典型实现。规范 §08:378 明令禁止。

### 9.8 存储失败的处置

| 失败类型 | 处置 |
| --- | --- |
| 容量超限（quota） | 显示"**本地备份失败**"，**保留内存内容**，**提供 Markdown 下载** |
| 存储禁用（unavailable，SecurityError） | 同上 |
| 值损坏（corrupt，JSON 解析失败） | 同上 |

**三条禁止**：

| 禁止 | 原因 |
| --- | --- |
| 禁止把 `e.message` 直接透出 | 会显示浏览器原始英文（如 `"The operation is insecure."`），与中文界面不一致。M6 W1 缺陷 F2 |
| 禁止显示"本地已保存" | 草稿实际**没存进去**（验收项 T10「不虚报本地已保存」） |
| 禁止清空编辑器内容 | 内存内容是最后一道防线 |

**退出账号**前提示未同步内容并允许下载。首版退出**只移除当前标签页 token**，并清理**当前会话**已同步或被用户明确丢弃的草稿，**不能自动删除其他窗口未同步内容**。

共享设备如需清除该账号全部本地草稿，**必须提供独立的明确确认操作**，提示会影响其他窗口。

### 9.9 生命周期事件的正确用法

| 事件 | 允许的用途 | **禁止**的用途 |
| --- | --- | --- |
| `beforeunload` | **仅在有未确认修改时**提供辅助离开提示 | 不能替代持续草稿与服务端确认 |
| `visibilitychange` | 可触发备份尝试 | 同上 |

> **非正常关闭可能损失尚未备份的最后一小段输入。** 不得在任何文案中承诺"绝对不丢失"。

## 10. 创建文档的响应丢失

**`POST /documents` 在响应丢失时不自动重发。**

| 规则 | 说明 |
| --- | --- |
| 处置 | **先提示用户刷新列表核对**，确认是否真的创建成功 |
| 理由 | 自动重发会生成**重复文档** |
| 离线时 | **不创建云端占位文档** |

> 后续如需完全自动重试创建，须**单独设计**客户端创建 ID 或幂等键协议。**首版不做。**

## 11. 冲突处理

### 11.1 冲突界面必须提供的四个选项

| 选项 | 行为 |
| --- | --- |
| **查看云端版本** | 展示服务端当前内容（只读） |
| **采用云端版本** | 用云端内容替换本地编辑区。**覆盖本地前必须让用户明确选择**，并保留可恢复草稿 |
| **将本地内容另存为副本** | 用本地内容 `POST` 一篇新文档 |
| **手动合并** | 用户编辑后提交 |

### 11.2 合并后的提交规则

**使用读取到的服务端版本提交**（即用 `server_version` 作为新的 `expected_version`）。

**若再次冲突，继续提示。不得无条件覆盖。**

### 11.3 冲突期间禁止的动作

| 禁止 | 原因 |
| --- | --- |
| 自动套用新版本覆盖云端 | 无声丢失用户编辑 |
| 自动套用本地覆盖云端 | 无声丢失云端修改 |
| 自动重发 `PUT` | 无限冲突循环 |
| 静默清除草稿 | 丢失唯一的用户副本 |
