## 2026-11-05 追加：M1 完成 R1/R2/R3 后的两条方法论

M1 把三项必修项全部做完并验证（真实传输用例 12→17，三类阶段定向变异全部检出）后，有两条**关于"怎么验证"而非"写什么"**的经验值得固化：

| ID | 依据 | 写法 |
|---|---|---|
| **M6-R16** | 排查中发现 M1 上一轮的变异残留污染了 `api.js` | **变异测试必须在副本上做**。直接在源文件注入再还原，一旦中途被打断或遗漏，就会留下**静默的破坏**（本次是一行 `clearTimeout` 提前执行，害我差点把"变异残留"误判为"R2 改法有问题"）。**养成习惯：`cp` 到临时目录 → 在副本上变异 → 只把"变异清单"和"检出结果"写进记录** |
| **M6-R17** | 我自己的两处变异设计缺陷导致误判 | **「变异未被检出」必须先排除变异本身无效**，才能判定用例鉴别力不足。常见两类：①标志位在 `finally` 里被重置，而 `finally` 先于外层 `catch` 执行 → 变异等价于原实现；②`String.replace` 只替换第一处，而目标锚点在文件里出现多次 → 改错了分支。**做法：用唯一锚点（如 `payload = await response.json()`）正则定位，并在注入后打印注入处上下文确认改对了地方** |

**R1 的实测发现（可复用）**：决定「响应头是否真正送达客户端」的是**延迟**而非 `flushHeaders()`——后者只保证数据写进 socket，不保证出网。实测四种组合：

| 组合 | 客户端拿到响应头 |
|---|---|
| 立即 destroy | 否 |
| 延迟 30ms destroy | 是 |

**结论**：构造"服务端已写出但客户端未收到"的场景，**必须留出传输窗口**，否则测的是另一个场景。

1. 收件前跑真实 runner，抽取计数与检查记录数字机器比对，不一致直接拒收 —— **W3 首次自然通过此项**
2. **变异测试作为收件流程的常规步骤**：W3 若做变异测试，M6 缺口在交件阶段即可发现，不必等 M1 补
3. 阶段记录加必填「实际执行环境：有终端已自执行 / 无终端已给步骤等用户执行」

[修复与鉴别力验证记录](../../deliverables/收件/W3/M6/R1R2R3_修复与鉴别力验证记录_20261105.md)。

### 两个真实缺陷（都是自己写的用例暴露的）

**缺陷一：捕获顺序 bug**——`makeFetchNotifyOnHeaders(fetchImpl, …)` 写在 `await start()` **之前**，
闭包捕获了 `fetchImpl` 的**旧值**（首次 `undefined`，其后为上一轮已关闭端口），
三个用例全部把请求打到错误服务端。修法：第一个参数改为**取值函数** `() => fetchImpl`。

**缺陷二：假时钟不模拟取消语义**——`makeTimers` 的 `clearTimeout` 只记录不取消，
于是「超时保护提前结束」这类变异在假时钟下**毫无影响**，
用例会误判为通过。修法：`clearTimeout` 真正标记失效，`trigger()` 返回布尔值表示是否仍有效。

### M2 变异的设计修正（方法论要点）

初版 M2 是**粗粒度**变异（改错误分类分支），连带破坏 5 个不相关用例——检出是真的，
但**无法证明检出点就是目标机制**。
改为**阶段定向**变异（只在 fetch 返回后清定时器）后，初版用例**漏检**，
暴露了初版用例的真实缺陷：**无法区分「超时覆盖正文读取」与「只覆盖 fetch 阶段」**。

> 这是 11-04 记录的教训（「缺少只改某一阶段行为的定向变异」）的**自我验证**：
> 定向变异确实抓出了自己写的用例的缺陷。**粗粒度变异能通过，不代表用例有效。**

### 新增规则

| ID | 依据 | 下一次写法 |
|---|---|---|
| **M6-R18** | 缺陷一（捕获顺序 bug） | **注入的依赖若会在测试中被重新赋值，必须惰性取值**（传 `() => x` 而非 `x`）。否则闭包捕获旧值 → 请求打到已关闭的服务端 → 表现为「断言未置位」或「归错错误类」，与被测逻辑无关 |
| **M6-R19** | 缺陷二（假时钟不取消） | **假时钟必须模拟被模拟对象的完整语义**：`clearTimeout` 要真正取消。只记录不取消，会让「保护提前结束」的缺陷在测试下隐形。`trigger()` 之类手动触发接口应返回布尔值，断言"定时器此刻仍有效" |
| **M6-R20** | M2 漏检 | **变异测试必须用阶段定向变异**（只改某一阶段行为），不能只改分类分支。粗粒度变异会连带破坏无关用例，检出点无法归因；定向变异漏检才暴露用例的真实盲区 |
| **M6-R21** | 即时断言的时序竞态 | **"某事件已发生"的断言要用 promise 等待，不能用即时布尔判断**。`await started` 恢复时，被测代码可能尚未走到目标调用点 → 误报失败。`await bodyRead` 既消除竞态，也确保断言的是「确实已发生」 |

### 新增规则

| ID | 依据 | 下一次写法 |
|---|---|---|
| **M6-R22** | 组员本周修复的 `clearDelay` 缺陷 | **凡是注入可控依赖（clock/delay/fetch）的函数，取消路径必须走同一套注入的取消接口**，不能写死全局 API。`delay` 与 `clearDelay` 必须成对注入；只注入 `delay` 时取消是空操作。**这是 R19「假时钟必须模拟被模拟对象的完整语义」在实现侧的对应要求** |
| **M6-R23** | 待写缓冲复活旧草稿（跨模块） | **写缓冲器无法知道"哪些键刚被清理"**——这类"清理后旧数据复活"的问题不是存储层能单方面修掉的。**正确处置是：识别出属跨模块接线顺序问题，写成交接约束交 M1，不硬凑一个假修复**。正确顺序：先 `flush()`/`cancel()` 再 `clearSessionDrafts()` |
| **M6-R24** | 三处契约冲突的处置方式 | **发现契约内部冲突时，标准处置是「写出两处原文 + 受影响行为 + 最小候选，不改代码不改断言」**。优先保持已冻结的契约（更严的一侧），并把文档措辞不一致作为**文档修正建议**提交 M1，不自行改协议 |
| **M6-R25** | 组员主动区分"用例错"与"源码错" | **失败时先区分三类：基线既有问题 / 本次引入问题 / 用例自身缺陷**。用例自身缺陷（如传错字段名、用 camelCase 传落盘形态字段）要**如实写明**"不是源码缺陷"，不能含糊带过 |
