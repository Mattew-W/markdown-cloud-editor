### 🟠 高-2 M5-03「不改变选区」断言无鉴别力；「保存状态变化不重建 textarea」无用例

**任务书第 22 行**：「**保存状态变化不重建 textarea、不改变选区**」。

**(a) 选区断言只是类型检查** —— `editor.dom.test.js:70-84`：

```js
contentInput.value = "abcdef";
contentInput.selectionStart = 2;
contentInput.selectionEnd = 4;
editor.setValue({ title: "t", content: "abcdef" });   // ← 内容相同，绕开重置分支
assert.strictEqual(contentInput, contentRef, "正文节点仍是同一引用");
assert.equal(typeof contentInput.selectionStart, "number");   // ← 对任何取值恒真
```

**M1 变异实测**（构造"坏"实现：setValue 后把选区推到末尾）：

```
坏实现后选区: 6 - 6          （原为 2 - 4，已被重置）
现有断言 typeof selectionStart === 'number' → 仍然通过（漏检！）
```

且用例刻意让 setValue 前后内容相同，绕开了 jsdom 的重置分支。实测 jsdom 行为：**赋同值选区不变；赋异值选区被推到末尾**（`HTMLTextAreaElement-impl.js:88-94`）。文件注释 `:81`「jsdom 中对 value 赋值不主动重置选区」**与 jsdom 实现不符**。

**(b) 断言对象错位** —— M5-03 要求的是「**保存状态变化**」时不重建 textarea。现有三个 DOM 用例测的都是 `setValue`（文档加载路径），**没有任何用例覆盖"同步状态变化"路径**。而"状态变化"恰是本周新增 `ui-feedback.js:229-238 renderSyncState` 的职责——它写 `#syncBadge`/`#statusText`，结构上不碰 textarea，但**没有断言证明这一点**。

**影响**：M5-03 是 W4 明确要求"逐条 DOM 断言"的编号项，也是 T13（`SYNC.md:118-126`「自动保存不得重建 `<textarea>`，否则焦点丢失、光标跳位、IME 组合输入被打断」）的落点。当前证据只覆盖"加载文档不重建节点"，**未覆盖"状态变化不重建节点/不动选区"**——对 IME 打断风险缺少直接防线。

**改法**：
1. 选区断言改为**具体数值**：记录 setValue 前后的 `selectionStart`/`selectionEnd`，断言不变。⚠ 需先明确语义边界：**加载路径**（setValue 换文档）允许重置，**保存路径**（状态变化）禁止重置——若采用"内容不同"场景，须在 `editor.js` 侧确认不写回，或在用例中显式声明这一区分。
2. 新增一例：构造含 `<textarea>` 的 DOM，调用 `uiFeedback.renderSyncState(...)`（dirty/saving/synced 与 storage failure 各一），断言 textarea **节点身份不变**、`selectionStart`/`selectionEnd` 不变、`previewElement` 不被重建。
