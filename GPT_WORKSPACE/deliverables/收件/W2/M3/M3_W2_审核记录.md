## 三、静态审阅：逐行 diff 比对

与下发基线 `materials/M3/token.rs`（SHA256 `8437f970cd063695`，274 行）比对，交件 `token.rs`（SHA256 `b9db575e04c96142`，384 行），**全部差异仅四类，无任何隐藏改动**：

### 1. 修复一：TTL 溢出 panic（`issue_token`）

基线（危险）：
```rust
let expires_at = now + Duration::seconds(i64::try_from(ttl_secs).unwrap_or(i64::MAX));
```

`unwrap_or(i64::MAX)` 把超大 TTL 静默转成 `i64::MAX`，随后 `Duration::seconds(i64::MAX)` **直接 panic**（chrono 越界）。

交件（修复）：
```rust
let ttl_secs = i64::try_from(ttl_secs)
    .map_err(|_| TokenError::Invalid("TTL 超出可表示范围".to_owned()))?;
let expires_at = now
    .checked_add_signed(Duration::seconds(ttl_secs))
    .ok_or_else(|| TokenError::Invalid("TTL 过大，过期时间溢出".to_owned()))?;
```

评价：**正确且最小**。转换失败与加法溢出两条路径都返回既有 `TokenError::Invalid`，接口签名不变，未引入新错误类型，未重构认证层。符合任务书"改为 checked 转换/加法，不改变接口"的要求。

### 2. 修复二：空 `sub` 被接受（`decode_token`）

交件在验签通过后增加：
```rust
if data.claims.sub.is_empty() {
    return Err(TokenError::Invalid("sub 不能为空".to_owned()));
}
```

评价：**正确**。JSON Web Token 规范允许 `sub` 为空字符串，但本项目 `sub` 承载用户 UUID（主项目 `middleware.rs` 用它做请求身份、`auth_db.rs` 用它查库），空值会导致"通过认证但查不到用户"的边界问题。任务书明确要求"UUID 用户标识至少不能为空"。

### 3. 新增 5 个边界测试

`正确签名但aud错误被拒绝`、`签名正确但缺aud被拒绝`、`签名正确但缺exp被拒绝`、`空sub被拒绝`、`ttl取u64max返回错误不panic`，并引入两个测试辅助结构 `ClaimsNoAud` / `ClaimsNoExp`。

评价：**覆盖到位**。缺 aud / 缺 exp 的构造方式正确——不是改坏 base64 去赌签名变化，而是用同构辅助结构重新序列化后**用正确密钥签名**，从而真正检验的是"字段缺失是否被拒绝"，而非"签名不匹配"。这比任务书里特意警告的做法更严谨。

### 4. 格式化

仅两处 import 排序（`use jsonwebtoken::{...}` 与 `use base64::{...}`），无逻辑改动。

### 依赖清单

`Cargo.toml` 相对参考版只保留实际使用的 `jsonwebtoken 9` / `chrono 0.4(serde)` / `serde 1(derive)` / `thiserror 2`，dev 依赖 `base64 0.22` / `serde_json 1`。**未引入 Actix / sqlx**，符合任务书"不引入 Actix/sqlx"。`serde_json` 补进 dev-dependencies 是必要的——基线测试代码用了 `serde_json::to_vec`。

### 5.2 M1 的一处加固：M3 修复仍留有一个 panic 缺口

M3 的修复为：

```rust
let ttl_secs = i64::try_from(ttl_secs).map_err(...)?;
let expires_at = now.checked_add_signed(Duration::seconds(ttl_secs)).ok_or_else(...)?;
```

**问题**：`Duration::seconds(ttl_secs)` 是**参数求值**，在 `checked_add_signed` 之前执行。当 `ttl_secs == i64::MAX` 时，`i64::try_from` **成功**（`i64::MAX` 是合法的 `i64`），但 `Duration::seconds(i64::MAX)` **本身就会 panic**——`checked_add_signed` 根本轮不到执行。

本机实测（`chrono 0.4.45`）：

```
i64::try_from(9223372036854775807) = Ok(9223372036854775807)
准备调用 Duration::seconds(9223372036854775807) ...
thread 'main' panicked at chrono-0.4.45/src/lib.rs:717:17:
TimeDelta::seconds out of bounds
```

即 M3 的用例 `ttl取u64max` 能通过（`u64::MAX` 超出 `i64` 范围，在第一道闸被拦下），但 **`ttl_secs == i64::MAX` 这条路径仍会 panic**。

**M1 的加固**：改用 chrono 的 `try_*` 版本，加一道闸：

```rust
let ttl_secs = i64::try_from(ttl_secs)
    .map_err(|_| TokenError::Invalid("TTL 超出可表示范围".to_owned()))?;
let ttl = Duration::try_seconds(ttl_secs)
    .ok_or_else(|| TokenError::Invalid("TTL 过大，超出时间间隔表示范围".to_owned()))?;
let expires_at = now
    .checked_add_signed(ttl)
    .ok_or_else(|| TokenError::Invalid("TTL 过大，过期时间溢出".to_owned()))?;
```

实测确认 `Duration::try_seconds(i64::MAX)` 返回 `None`（不 panic），故三道闸完整覆盖。

**补充的回归测试**：

```rust
#[test]
fn ttl取i64max返回错误不panic() {
    // u64 → i64 转换能成功，但秒数已超出 chrono TimeDelta 的表示范围，
    // `Duration::seconds` 在此处就会 panic，必须走 `try_seconds`。
    let res = issue_token("u1", "alice", SECRET, i64::MAX as u64);
    assert!(res.is_err(), "i64::MAX TTL 必须返回错误而非 panic");
}
```

> **影响评估**：该缺口在当前生产路径下**不可达**——`config.rs` 的 `Config::new` 已把 TTL 限制在 `MIN_JWT_TTL_SECS(60)..=MAX_JWT_TTL_SECS(86400)`，而 `routes/auth.rs` 的两个 `issue_token` 调用点都传 `config.jwt_ttl_secs`。但 `issue_token` 是 `pub` API，且这是 panic 而非错误返回（panic 会连带中断 Actix worker 线程），加固成本极低，值得补上。
