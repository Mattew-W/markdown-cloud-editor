# M3 W2 变更说明

本变更说明按任务要求区分三类：**原模块已有**、**本次新增测试**、**发现缺陷与候选修复**。每个修复均对应真实失败/通过证据（见 `检查记录.md` 与各日志）。

## 1. 原模块已有（非本人从零实现）
`jwt_review/src/token.rs` 的签发与验签主体为随包 `materials/M3/token.rs` 的工作副本：
- `Claims` 结构、`TokenError` 枚举（Invalid/Expired/NotYetValid）。
- `issue_token`：HS256 签发，含随机时刻的 `iat`/`exp`、固定 `iss`/`aud`。
- `decode_token`：固定 HS256（不信任 header 的 `alg`）、校验签名/exp/iss/aud，leeway=0。
- 原模块自带 8 个测试（正常、错误密钥、篡改载荷、篡改签名、非 JWT、过期、错 issuer、alg=none）。

## 2. 本次新增测试（M3 W2 阶段 2）
在 `src/token.rs` 测试模块新增 5 个边界用例，并引入两个测试辅助结构（`ClaimsNoAud`、`ClaimsNoExp`，用于构造签名正确但缺字段的 token）：
1. `正确签名但aud错误被拒绝` — 错误 aud 拒绝。
2. `签名正确但缺aud被拒绝` — 缺 aud 拒绝。
3. `签名正确但缺exp被拒绝` — 缺 exp 拒绝。
4. `空sub被拒绝` — 空 sub 拒绝。
5. `ttl取u64max返回错误不panic` — ttl=u64::MAX 返回错误、不 panic。

## 4. 概念自述（用自己的话）
- **签名保证什么**：HS256 签名是"只有持有同一密钥的人才能生成的有效 token"的证明。验签通过表示该 token 确实由掌握密钥的签发方生成、内容未被篡改；但签名本身不约束"内容应该是什么"，内容的正确性还要靠 `iss`/`aud`/`sub`/`exp` 等声明校验。
- **aud 检查什么**：`aud`（受众）校验 token 是为"谁"签发。`decode_token` 要求 aud 必须等于 `markdown-cloud-editor-web`，防止"签发给别的服务的 token 被本服务误用"。
- **iss 检查什么**：`iss`（签发者）校验 token 是"谁"签发的。要求 iss 等于 `markdown-cloud-editor`，防止其他系统签发的 token 冒充本系统。
- **为什么知道 token 内容不等于能修改它**：JWT 的载荷只是 base64 编码、可被任何人读取（明文），但它连同 header 一起被签名；签名密钥不在 token 里、客户端拿不到。攻击者能读出并改内容，却算不出与新内容匹配的有效签名，所以改动后的 token 验签必失败。
- **我尚不理解的点（待与 M1/同学确认）**：
  1. `sub` 只做了"非空"校验，是否还需要校验必须是合法 UUID 格式？任务仅要求非空，未展开。
  2. `username` 字段当前未做任何校验（可空/任意），是否有类似的最小校验要求？
  3. leeway=0 意味着时钟偏差零容忍，分布式环境下是否会造成真实用户的误判、是否需在路由层处理？
