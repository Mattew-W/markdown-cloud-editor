## 5. 变异测试：证明脚本具备证伪能力

只跑通过的脚本说明不了问题——必须证明它**能检出问题**。M1 构造 8 个变体，各自独立建库独立运行：

| 变体 | 手法 | 实测 | 判定 |
|---|---|---|---|
| M0 基线 | 未变异 | rc=0，11 PASS | ✔ 符合预期 |
| M1 | 移除 `version > 0` 约束 | rc=3，失败于 `version = 0` | ✔ 检出 |
| M2 | 移除 content 262144 约束 | rc=3，失败于 `content 262145 bytes` | ✔ 检出 |
| M3 | 移除标题非空约束 | rc=3，失败于 `empty title` | ✔ 检出 |
| M4 | 移除 username 唯一约束 | rc=3，失败于 `duplicate username` | ✔ 检出 |
| M5 | 移除 owner 外键 | rc=3，失败于 `nonexistent owner` | ✔ 检出 |
| M6 | title 放宽为 VARCHAR(512) | rc=3，失败于 `title 256 chars` | ✔ 检出 |
| M7 | 用例3 预期码误写为 23503 | rc=3，失败于 `version = 0` | ✔ 检出 |

**8/8 全部符合预期。** 结论：脚本不是"永远报 PASS"的空壳，每条断言都真的绑定了对应约束；错误码不符同样会被判失败（M7 证明"不能只看出错"这条要求被真正落实）。

### 5.1 事务隔离性单独验证

M8 变体（故意让**第一个**用例的预期码错误）实测 rc=3、整轮失败、后续用例未继续——这**不是漏检**，而是任务书明确要求的行为："没有报错或错误码不同，都显式 RAISE EXCEPTION 使整轮失败"。若相反（失败后继续跑），反而是"失败被误判为通过"。

隔离性的正面证据（独立最小实验）：

```
case1_state=23505          ← 重复 username 失败，被嵌套子事务捕获
case2_state=23503          ← 后续负例继续执行，同样被捕获
outer_tx_usable_users=1    ← 外层事务未被中止
case3_legal_insert_state=00000  ← 后续合法写入成功
```

**嵌套 BEGIN/EXCEPTION 子事务确实隔离了单条失败，外层事务保持可用。** 交付说明第六节第 3 问的解释与实测一致。
