## 3. 真实浏览器验证（唯一一项离开 Node 的验证）

**为什么必须做**：mock 测试断言 `input.pathname` 恰好正确，会掩盖「请求最终发往错误域名」这类缺陷。真实浏览器才能暴露。

| # | 动作 | 实际输出 | 断言 |
| --- | --- | --- | --- |
| N1 | 在真实 Chromium 149 页面中执行 `new URL('/api/v1/documents', 'http://dummy-base')` 并取 `href` | `http://dummy-base/api/v1/documents`，`origin = http://dummy-base` | 该形式会指向不存在的外域 ✅ |
| N2 | 用上述绝对 URL 发起 `fetch` | `Failed to fetch`；捕获到的请求 `GET http://dummy-base/api/v1/documents (失败: net::ERR_NAME_NOT_RESOLVED)` | **真实后端永远收不到请求** ✅ |
| N3 | 现行实现传相对路径 `"/api/v1/documents"` | 由浏览器按当前页面 origin 解析，不产生 `dummy-base` 请求 | 修法正确 ✅ |

**结论**：交件原写法（`new URL(path, 'http://dummy-base')`）是致命缺陷，已改为相对路径直传。

## 5. 已知取舍

| 项 | 取舍 | 理由 |
| --- | --- | --- |
| 服务端 `error.message` 原样透传为异常 message | 保留 | `API.md` §4.1 明确「message 仅供显示，客户端不得依赖文字内容做逻辑分支」。**注意区分**：不透出的是 JS 异常的 `e.message`（如 `socket drop`），那会暴露内部细节；服务端业务提示按契约透传 |
| `request_id` 优先取响应体，缺失时回落 `X-Request-Id` 头 | 保留 | `API.md` §4.1 称 request_id「关联 X-Request-Id 响应头，用于排障」，响应体缺失时若无回落则无法排障 |
| 2xx 中仅 204 特判返回 `null`，其余（202/206 等）解析 JSON | 保留 | `API.md` §1：「除 204 外，成功与错误响应均为 JSON」。已加测试钉住该边界 |
| 不提供 `GET /health` 专用方法 | 保留 | 契约明示该接口**不带** `/api/v1` 前缀，不属本模块范围 |
| 不自动重试 | 保留 | 契约明文禁止。重试与退避属 `sync.js`（M1） |
