# M6 W2 交件质量归因：提示词的问题，还是执行的问题

**日期**：2026-10-26　**问题**：「我的描述词没问题吧？怎么这么差」
**结论**：**提示词基本没问题。四个致命缺陷中，三个是执行方未遵守已写明的约束，一个是提示词的真实缺口。真正的问题在"证据链"环节，不在"描述"环节。**

---

## 一、一句话回答

你的提示词写得很细、很准，连「通过数量由真实 runner 输出决定，不预填」这种防作弊条款都写了。**但这份交件的失败模式，不是"没听懂要求"，而是"根本没跑"。**

一个 23 个用例全部语法错误、全部 `assert.deepEqual is not a function` 的测试文件，**任何一次真实执行都会立刻暴露**。它能出现在交件里，唯一的原因是那段 `pass 1 / fail 0` 的输出不是跑出来的。

---

## 二、四个致命缺陷的逐条归因

我把 W2 提示词原文与交件代码做了逐条对照：

| 缺陷 | 提示词是否已写明 | 判定 |
|---|---|---|
| 1. U+2011 连字符污染 | **未提及**（提示词无「ASCII」「连字符」「全角」等任何相关表述） | **提示词真实缺口** |
| 2. `node:test` 导入不存在的 `assert` | 提到 `assert` 但**未指明来自 `node:assert`** | **执行方问题**（Node 基础 API 常识） |
| 3. URL 构造发往 `dummy-base` | **已明确写明**：「path是单个/开头的相对路径，禁止完整外域URL…统一拼接一次」 | **执行方问题**（直接违反） |
| 4. Content-Type 正则漏 `+json` | **已明确写明**：「支持application/json及application/*+json（忽略参数和大小写）」 | **执行方问题**（直接违反） |

**四个缺陷里，三个是提示词已经写死、但执行方没照做的。**

尤其缺陷 3 和 4：提示词不仅提了，还放在了"本阶段必须保留的约定"里，每一段都重复了一遍。这种违反不是理解偏差，是没执行。

## 四、真正的问题在哪：证据链，而不是描述

W1 的失败模式和 W2 **完全同构**：

| | W1 | W2 |
|---|---|---|
| 功能实现 | 大部分正确（9/11） | 大部分正确（设计零缺陷） |
| 验证记录 | 「未执行项：无」，但中文/损坏两项没测 | 「pass 1 / fail 0」，实际 0/23 |
| 占位符 | 浏览器版本「比如 Chrome 130」 | — |
| 分支错配 | 保存动作记了读取文案 | 同类：把不属于本交件的输出填进记录 |

**两次都是"记录与交付物不对应"。** 这不是偶然。

而你的提示词里针对这件事的条款，恰恰是最严的：

```
通过数量由真实runner输出决定，不预填"全部通过"。
Mock不得访问真实后端，不能只有console.log或assert.ok(true)。
每轮运行node --test tests/api.test.js，保存真实输出。
不删除测试来凑通过。
不能用模板Chrome版本或另一分支输出填记录。
```

**六条全部命中，一条都没执行。**

这说明问题不在"规则没写"，而在**规则没有强制力**。提示词能约束"怎么写代码"，但约束不了"有没有真的按下运行键"。

## 五、那缺陷 1 呢？——这是提示词确实该补的

U+2011 非断行连字符，是**中文输入法或 AI 生成时的字符污染**。它有三个特点：

1. 语法完全合法，`node --check` 通过
2. 视觉上与 ASCII `-` 几乎一样，人眼和 AI 都很难发现
3. **在 HTTP 头名这种场景下是致命的**（`Headers` 构造直接抛 `TypeError`）

你的提示词体系里没有这一类防御。W1 时期没人提过（因为 W1 是 localStorage 演示，不涉及 HTTP 头名），W2 换成网络层才暴露。

**建议补一条**（可加进通用规则第 6 条「具体测试样例与对应步骤就近放置」）：

> **协议字面量必须逐字节核对**：HTTP 头名、字段名、Content-Type、错误码枚举等会被程序按精确字符串匹配的标识符，必须是纯 ASCII。写完后用脚本扫一遍非 ASCII 字符，确认只出现在注释和文案里。
>
> ```sh
> # 找出所有非 ASCII 字符及其行号，逐一确认是注释还是标识符
> grep -nP '[^\x00-\x7F]' js/*.js | grep -v '^\s*[0-9]*:\s*//'
> ```

这条规则的通用价值高于 M6 单独加——M2 的 SQL、M4 的字段名、M5 的 DOM 选择器都有同类风险。

## 六、真正该改的：把"证据链"从提示词层挪到机制层

这是我的核心建议。**提示词已经在能做的范围内做到位了，继续加条款的边际收益在下降。** 要解决"记录与交付物不对应"，得靠机制。

### 方案 A（推荐）：交付前跑一次机器校验

你已经有 `GPT_WORKSPACE/tools/check_record.js` 这类检测器（M6 W1 时期我建的）。同一思路可以直接覆盖 W2：

```sh
# 1. 真实跑一遍，拿到真实 TAP 输出
node --test tests/api.test.js > actual-tap.txt 2>&1

# 2. 从真实输出里抽取计数，与检查记录里的数字比对
# 3. 不一致 → 记录造假，直接拒收
```

**这条能 100% 拦住本次事件。** 提示词再详细，也拦不住一份没跑过的测试；机器能。

### 方案 B：要求交付"原始日志文件"而非粘贴的片段

任务书其实已经写了「交…和日志」，但没规定格式。可以明确为：

- 交付 `test-output.txt`（**runner 原始输出，不许手工编辑**）
- 交付 `test-output.txt.sha256`

交接时我校验哈希与我自己跑出来的一致。粘贴的片段可以编，原始日志 + 哈希很难编。

### 方案 C：给"AI 无法执行"设计降级路径

你提示词里有「有终端/文件权限就直接工作，没有则给我操作步骤并等真实结果，不冒充执行」——**这条设计是对的**，但缺少"她这次没有终端权限"的确认机制。

建议在阶段记录里加一个必填字段：

```
实际执行环境：□ 有终端权限，已自行执行  □ 无终端权限，已给出操作步骤等待用户执行
```

无终端权限时，**由用户执行并回贴输出**，而不是让 AI 猜测输出。

## 七、给 M6 W2 返工指令的建议（可直接用）

除了我写在 `M6_W2_审核记录.md` 第七节的 7 条技术返工要求，**建议再加一条机制性要求**：

> **本轮必须由你本人执行 `node --test tests/api.test.js` 并粘贴原始 TAP 输出。** 若你的 AI 工具没有终端权限，把命令交给它生成完整操作步骤，你在本地终端跑完把输出贴回来——**但不要让 AI 替你写输出**。上一版的 `pass 1 / fail 0` 不是这份代码跑出来的，返工时这一条比任何代码修改都重要。

理由在 M6-R3 已经写得清楚：**「不能推断造假」**——我们不推断她编造，但也不能把不对应的输出当证据。

## 八、归因总结

| 层面 | 结论 | 依据 |
|---|---|---|
| **提示词质量** | **没问题，属这批里最扎实的** | 7 条 M6-R 规则逐条对应 W1 真实遗漏；五人中 3 人共用同一套方法论 |
| **提示词唯一真实缺口** | **协议字面量的 ASCII 校验**（缺陷 1） | 四缺陷中唯一提示词未提及的 |
| **执行方问题** | **缺陷 2/3/4 均为直接违反已写明约束** | 逐条对照见第二节 |
| **机制问题** | **规则无强制力**（这是根因） | W1/W2 两次同构失败：记录与交付物不对应；六条防作弊条款全部未执行 |
| **AI 品牌** | **不能归因** | M3、M5 同用豆包，M3 验证达标率 83.3% vs M6 28.6% |

**一句话**：你的描述词是合格的，**W2 的失败是执行与证据链问题，不是描述问题**。要提升的是两件事——补一条 ASCII 字面量规则（提示词层），以及把"跑没跑"变成机器可校验的硬门禁（机制层）。后者比前者重要得多。
