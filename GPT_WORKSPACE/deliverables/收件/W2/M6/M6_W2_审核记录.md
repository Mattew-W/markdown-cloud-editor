## 二、四个致命缺陷（全部经实测确认）

### 缺陷 1（致命）· 源码混入 U+2011 非断行连字符

`js/api.js` 三处 HTTP 头名使用了 **U+2011 NON-BREAKING HYPHEN**（`‑`），而非 ASCII `-`（U+002D）：

| 行号 | 实际内容 | 问题 |
|---|---|---|
| `:100` | `headers.set('Content‑Type', 'application/json')` | 头名非法 |
| `:138` | `res.headers.get('content‑type')` | 永远取不到值 |
| `:168` | `res.headers.get('retry‑after')` | 永远取不到值 |

**实测报错**（Node 22 / `Headers` 构造时）：

```
TypeError: Cannot convert argument to a ByteString because the character at
index 9 has a value of 8209 which is greater than 255.
```

`tests/api.test.js` 中同样大量使用 U+2011（`'my‑token‑123'`、`'retry‑after'`、`'req‑001'`、`'M6‑W2'` 等），包括 describe/it 的测试名。

**影响**：所有请求在构造 header 阶段就抛 `TypeError`，**一个请求都发不出去**。`retry-after` 取不到值意味着即使修好前面，`RateLimitedError.retryAfter` 永远是 `null`。

**根因推测**：AI 生成或输入法转换时产生的同形字替换。**这类问题静态审阅看不出来，语法检查也过（`node --check` 通过）——只有真跑才会暴露。**

### 缺陷 2（致命）· `node:test` 导入了不存在的 `assert`

`tests/api.test.js:1`：

```js
import { describe, it, assert } from 'node:test';
```

**Node 的 `node:test` 不导出 `assert`**。断言 API 属于 `node:assert`。实测：

```
TypeError: assert.deepEqual is not a function
TypeError: assert.equal is not a function
```

**影响**：23 个用例全部因同一个原因失败，与被测代码无关。

### 缺陷 3（致命）· URL 构造发往不存在的外域

`js/api.js:80`（原版）：

```js
const url = new URL(`${BASE_URL}${path}`, 'http://dummy-base');
```

用假 base 拼出**绝对 URL** 再交给 `fetch`。浏览器会把请求发往 `dummy-base` 这个不存在的域。

**真实 Chromium 实测**：

```
api.js 构造出的绝对 URL : http://dummy-base/api/v1/documents
  其 origin            : http://dummy-base
fetch 实际结果: "Failed to fetch"
捕获到的请求:
   GET http://dummy-base/api/v1/documents
   GET http://dummy-base/api/v1/documents (失败: net::ERR_NAME_NOT_RESOLVED)
```

**影响**：即使前两个缺陷都修好，这个模块在浏览器里**永远收不到任何响应**，真实后端一个请求都收不到。

**正确写法**：直接传相对路径给 `fetch`，由浏览器按当前页面 origin 解析：

```js
const url = `${BASE_URL}${path}`;   // '/api/v1/documents'
```

> 原测试 `assert.equal(input.pathname, ...)` 之所以"看起来对"，是因为 mock fetch 拿到的是 URL 对象，`.pathname` 恰好正确——**测试写法掩盖了真实缺陷**。这正是「Mock 不得访问真实后端」条款的盲区：mock 验的是路径拼接，不是最终会不会发到对的地方。

### 缺陷 4（中）· Content-Type 正则漏掉 `+json` 后缀

`js/api.js:140`（原版）：

```js
const isJsonContentType = /^application\/(\*\+)?json/.test(contentType);
```

**实测行为**：

| Content-Type | 原正则 | 期望 |
|---|---|---|
| `application/json` | MATCH | MATCH |
| `application/json; charset=utf-8` | MATCH | MATCH |
| `application/vnd.api+json` | **NOMATCH** | MATCH |
| `application/problem+json` | **NOMATCH** | MATCH |
| `application/jsonx` | MATCH | NOMATCH |

任务书阶段2 原文要求「支持application/json及application/*+json（忽略参数和大小写）」，**`+json` 后缀是协议明确要求，漏匹配会直接导致错误体不被解析**。

## 三、设计层面做对的部分（应予肯定）

| 项 | 证据 |
|---|---|
| 零 DOM | 全文无 `window`/`document`/存储访问，符合「零DOM网络库」约定 |
| 接口签名与任务书完全一致 | `apiFetch(path, {method,token,body,fetchImpl,timers})`、`BASE_URL='/api/v1'`、`TIMEOUT_MS=10000` 全部吻合 |
| 九类 `error.code` 映射 | 与 `API.md` §4.1 逐条核对，**9/9 完全一致**，无遗漏无多余 |
| 两种 409 未混淆 | `USERNAME_TAKEN`→`ConflictError`，`VERSION_CONFLICT`→`VersionConflictError` |
| `serverVersion` 不编造 | `details.server_version` 缺失或非正整数时抛 `ProtocolError`，不填默认值 |
| `Retry-After` 保留原始字符串 | 交上层解析，不自行换算 |
| 204 不调 `json()` | 单独分支直接 `return null`，且测试用"json() 抛错"证明确实没调用 |
| 按 code 分支不按 message | 符合协议「客户端不得依赖文字内容」 |
| 不自动重试 | 实现无重试逻辑 |
| 错误不暴露 HTML | 非 JSON 错误体走 `http status ${code}`，不把 HTML 塞进 message |
| 定时器 finally 清理 | 成功/业务失败/解析失败/网络失败均走 `finally` |
| 交付说明三问回答到位 | 204 不读 JSON、409 传 serverVersion、超时不能断言服务器未保存——**第三问的答案「请求已发出，服务端可能已完成写入，只是响应没回来」是准确的**，符合规范 §08「结果未知」语义 |

**这三点说明组员理解了任务意图，不是套模板。** 返工应当保留现有设计，只修实现缺陷。
