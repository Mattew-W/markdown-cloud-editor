二、完成项
═══════════════════════════════════════════════════════════════

1. 零 DOM 网络库。不读写任何 DOM、不绑定事件、不访问存储。
2. apiFetch(path, {method, token, body, fetchImpl, timers}) 单一请求函数，
   未扩散成许多随意命名的方法。
3. BASE_URL='/api/v1'、TIMEOUT_MS=10000 两个常量。
4. path 校验：必须单个 / 开头；拒绝完整外域 URL、// 协议相对、
   重复 /api/v1 前缀。非法路径在构造请求前就抛错，不发请求。
5. Bearer 只放 Authorization 头，不进 URL；body 非 undefined 才
   JSON 序列化并设 Content-Type；GET 不接受 body。
6. 成功 200/201 返回 JSON；204 直接返回 null 且绝不调用 response.json()。
7. 九类 error.code → 专用错误类，按 code 分支不按 message；
   两种 409（USERNAME_TAKEN / VERSION_CONFLICT）不混淆。
8. VersionConflictError 携带 serverVersion；缺失或非法抛
   ProtocolError，不编造版本号。
9. RateLimitedError 保留原始 Retry-After 头字符串，解析与退避交上层。
10. 非 2xx 先查 Content-Type，支持 application/json 与
    application/*+json（忽略参数与大小写）；非 JSON 不硬解析；
    声明 JSON 但损坏抛 ProtocolError；未知 code 归基类并保留 status。
11. 10 秒 AbortController 超时，计时范围覆盖 fetch 与响应体读取；
    成功/业务失败/解析失败/网络失败四条路径都清理定时器。
12. 网络层失败归 NetworkError；超时归 TimeoutError。
13. 不自动重试：任何失败都只发一次请求。
14. 错误文案一律中文，不透出 JS 异常的 e.message。
15. Node 内置测试 50 项，另有前端合计 97 项全部通过。

在页面中使用（浏览器）：
  <script type="module">
    import { apiFetch, AuthError } from './js/api.js';
    try {
      const doc = await apiFetch(`/documents/${id}`, { token });
    } catch (err) {
      if (err instanceof AuthError) { /* 跳登录 */ }
    }
  </script>

本模块是纯逻辑网络层，不需要启动服务器。接真实后端后由页面同源调用。

═══════════════════════════════════════════════════════════════
五、三个问题的解释
═══════════════════════════════════════════════════════════════

【问题 1】204 为什么不读 JSON？

HTTP 规范规定 204 No Content 响应不得包含响应体。调用
Response.json() 会尝试解析一个空体，抛出 SyntaxError，把一次正常的
"删除成功"变成一个看似严重的解析错误。所以必须先判
response.status === 204 直接返回 null。

测试验证方式不是看代码，而是让 mock 的 json() 一旦被调用就抛错，
再断言它没被调用（检查记录 A3 项：response.json() 是否被调用 = false）。

【问题 2】409 如何把 serverVersion 交给上层？

两种 409 必须分开：
  USERNAME_TAKEN   → ConflictError          （注册页提示换名）
  VERSION_CONFLICT → VersionConflictError   （进 conflict 状态）

VERSION_CONFLICT 时，从错误体的 details.server_version 读出服务端当前
版本，存进异常实例的 serverVersion 属性。上层捕获后直接用
err.serverVersion 就能拿到，不必再解析原始响应。

关键点：server_version 缺失或不是正整数时，抛 ProtocolError 而不是
补一个默认值。编造版本号会让上层基于假数据做冲突合并，比直接失败更危险。
检查记录 F1–F6 用六种非法值验证了这条。

【问题 3】超时为什么不能断言服务器一定没保存？

客户端 10 秒超时，只表示客户端放弃了等待响应，不表示服务端没执行。
HTTP 请求已经发到网络上，服务端可能已经完成了数据库写入，只是响应
报文没能返回客户端——网络中断、连接被重置、中间代理超时都可能造成这种
"结果未知"状态。

若此时客户端直接判定"没保存"并重发 PUT，会用同一个 expected_version
再写一次。乐观锁会把它变成 VERSION_CONFLICT，用户看到冲突，但内容其实
早就保存好了。

正确做法是按 SYNC.md §6 的"结果未知"流程：读取云端记录核对——
  1. 云端内容与发送快照完全相同 → 确认已持久化，接收读到的版本；
  2. 云端版本仍等于发送快照的 base_version → 用原 expected_version 重试；
  3. 云端版本已变且内容不同 → 进 conflict，禁止自动覆盖；
  4. 读取返回 404 → 保留本地内容，提示云端文档已不可用。

TimeoutError 与 NetworkError 都属于这一类，不能当作"未保存"处理。
