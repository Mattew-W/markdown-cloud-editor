## 六、发现并修复的生产缺陷（`clearDelay`）

### 现象（组员自己先跑红发现）

```
not ok 18 - M6-03 待写缓冲：cancel 后清理，定时器到点不会复活旧草稿
  error: cancel 必须真正取消注入时钟的定时器
not ok 19 - M6-03 待写缓冲：先 flush 落盘再清理，同样不留残留
not ok 22 - M6-04 flush 真正取消注入时钟的旧定时器
not ok 23 - M6-04 flushAll 落盘且不再触发第二次写入
# tests 25 / # pass 20 / # fail 5
```

### 根因

`createDraftWriter` 的取消路径写死 `clearTimeout(timer)`。注入可控/假时钟时，句柄不在全局时钟名下 → `flush()/flushAll()/cancel()` 取消是**空操作** → 旧定时器仍到点触发 → 把**之后新排入**的草稿提前写走。

**这不是测试问题，是真实的生产缺陷**（任何注入了 `delay` 的调用方都会踩到）。

### 修复（+7 / −3 行）

```js
const clearDelay = options.clearDelay ?? ((handle) => clearTimeout(handle));
// flush / flushAll / cancel 中的 clearTimeout(timer) → clearDelay(timer)
```

**接口影响**：冻结的 7 个导出签名**零变化**（`INTERFACES.md` §2.3）；`createDraftWriter` 本不在冻结清单内，新增的是**可选**参数；不传时默认全局 `clearTimeout`，**生产行为与基线一致**。

**M1 独立验证**：主项目合入该修复后，137 → 162 全绿，**未破坏任何现有行为**；V8 变异（把 `clearDelay` 改成空操作）被新增用例检出 4 项。

### 一处值得肯定的诚实

组员在检查记录 §4.1 明确写出：**第 5 个失败是她自己用例的缺陷**（`classifyRestore` 入参是落盘记录，她最初传了 camelCase `baseVersion` 导致 `base_version` 为 `undefined`），并注明"**不是源码缺陷**，已改用 `base_version` 后通过"。

**主动区分"用例错"与"源码错"，并引用 M6-R21 先排除用例自身的取值/时序错误**——这是很少见的严谨。

### 冲突 2：恢复分类是三分支还是四分支（影响 M6-04）

**结论：冲突真实存在。组员按三分支回归是正确的**，并明确「若任务书确指 §6.2，应由 M1 在 `sync.js` 实现，M6 不越界」。

### 冲突 3：`base_version` 要 `Number.isFinite()` 还是 integer（影响 M6-02）

## 八、待写缓冲复活问题（跨模块，交接给 M1）

这是本次最有价值的发现之一。组员用 `证据/probe_buffers.mjs` 实测三条路径：

| 顺序 | 清理后条数 | 旧定时器是否仍触发 | 到点后内容 | 结论 |
|---|---|---|---|---|
| A 直接清理（不 cancel / 不 flush） | 0 | **true** | `["旧会话草稿"]` | **复活** |
| B 先 `cancel()` 再清理 | 0 | false | `[]` | 不复活 |
| C 先 `flush()` 再清理 | 0 | false | `[]` | 不复活 |

**组员的定性准确**：`drafts.js` 没有"记住哪些键被清理"的职责，**A 路径的复活属跨模块接线顺序问题，不是草稿层能单方面修掉的缺陷**；按 `SYNC.md` §8.1「先保存本地草稿 → 再生成新 edit_session_id」的正确顺序即不会发生。

**处置**：写入 `M1交接表.md` §3，要求切换文档/退出账号时**先 `flush()` 或 `cancel()`，再 `clearSessionDrafts()`**；用例侧守护 B、C 两条安全路径。

**M1 认可这个定性并采纳该约束。**
