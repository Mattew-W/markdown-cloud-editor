## 一、为什么要修

## 二、4 处空缺与修法

### GAP-1 / GAP-2：`clearSessionDrafts` 的 docId 与 userId scope 未被真正检验

**原用例为什么检不出**（`drafts.w4.test.js` 的「只清本用户/本文档内已证实可弃的旧会话」）：

```js
saveDraft(draftOf({ docId: DOC_2,  sessionId: SESS_2, content: '别的文档' }), store);
saveDraft(draftOf({ userId: USER_B, sessionId: SESS_2, content: '别的账号' }), store);

const res = clearSessionDrafts(root, { cloud: { version: 9, title: '旧标题', content: '已上云' } }, store);
assert.equal(listDrafts({ userId: USER_A, docId: DOC_2 }, store).length, 1, '不得影响其他文档');
```

这两条对照记录的 `content` 是 `'别的文档'` / `'别的账号'`，**与 cloud 的 `'已上云'` 不一致** → `isCoveredByCloud` 返回 false → **那两条记录本来就不在可删集合里**。

于是：**无论 scope 前缀怎么写，这条断言都会通过。**

> 把 `clearSessionDrafts` 的 prefix 改成不含 `docId`，全套 162 项**依然全绿**。

**修法**：新增两条用例，让对照记录**与 cloud 完全一致**——这样它才真的可能被误删，断言才真正约束了 scope。

```js
test('M6-03 不得误删「其他文档」中已被云端覆盖的草稿', () => {
  const cloud = { version: 9, title: '旧标题', content: '已上云' };
  saveDraft(draftOf({ sessionId: SESS_2, title: cloud.title, content: cloud.content }), store);
  saveDraft(draftOf({ docId: DOC_2, sessionId: SESS_2, title: cloud.title, content: cloud.content }), store);
  const res = clearSessionDrafts(root, { cloud }, store);
  assert.deepEqual(res.removed, [buildDraftKey({ userId: USER_A, docId: DOC_1, sessionId: SESS_2 })]);
  assert.equal(listDrafts({ userId: USER_A, docId: DOC_2 }, store).length, 1,
    '其他文档的草稿即使与云端一致也不得被删——scope 过滤必须含 docId');
});
```

账号维度同理（`USER_B` 的记录也与 cloud 一致）。

### GAP-3：`MERGE_WINDOW_MS === 250` 无任何断言

原用例验证了「窗口内合并、到点写一次、落盘值是最后一次」，但**没有钉住窗口长度本身**——把 250 改成 10，用例仍然全绿。

**修法**：加两条，一条钉导出常量，一条钉**实际排入延迟队列的那个值**：

```js
test('M6-04 合并窗口必须是 250 毫秒', () => {
  assert.equal(MERGE_WINDOW_MS, 250, '合并写入窗口必须是 250 毫秒');
});

test('M6-04 实际排入的延迟必须就是 250 毫秒（假时钟记录到的值）', () => {
  writer.schedule(draftOf({ content: '一次输入' }));
  assert.equal(clock.msOf(clock.ids()[0]), 250, '排入的延迟必须是 250 毫秒');
});
```

第二条需要在 `makeClock()` 里补一个 `msOf(id)` 读回排入时的 `ms`（假时钟本来就把 `ms` 存下来了，只是没有用例去读）。

> 第二条防的是「常量是 250、实际排入用别的值」这类不一致——只钉常量挡不住它。

### GAP-4：`saveDraft` 返回值的 `recordedAt` 未被 W4 断言

原用例校验的是**落盘后读回**的 `recorded_at`（正确），但 `saveDraft` 的**返回值**同样会直接进界面与日志——那 25 项里没有断言它。

> 注：旧用例 `drafts.test.js` 有兜底，所以全套能检出；**但本周新增的 25 项对该处无鉴别力**。

**修法**：

```js
test('M6-02 saveDraft 返回的 recordedAt 也必须可解析（返回值是调用方直接用的）', () => {
  const result = saveDraft(draftOf(), store);
  assert.equal(typeof result.recordedAt, 'string');
  assert.equal(Number.isNaN(Date.parse(result.recordedAt)), false,
    'saveDraft 返回的 recordedAt 不能是 Invalid Date');
  assert.equal(result.recordedAt, JSON.parse(store.stats.writes[0].raw).recorded_at,
    '返回值与落盘值必须是同一个时间戳');
});
```

## 四、给 M6 本人的一条通用经验

> **「不得误删 / 不得影响」这类断言，要先问一句：如果过滤完全失效，这条断言会不会变红？**

如果对照记录**本来就不在被作用的集合里**，那这条断言测的不是你以为的东西。

有效的构造条件是：**让对照记录落在「确实可能被误删」的位置上**——本例就是让其他文档/账号的记录**与 cloud 完全一致**。
