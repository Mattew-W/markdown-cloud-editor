三、一个执行期缺陷（已修，值得记录）
-----------------------------------

v2 首次运行时 `npm test` **进程不退出**（HANG > 45s）。
逐文件二分定位到 `app.state.w5.test.js` 的第一个用例（dirty）。

根因链：
  1. 该用例断言在输入后 30ms 内完成，此时 sync.js 的**防抖定时器（1.5s）尚未到期**；
  2. 测试结束、server 已关闭，但定时器仍在挂载 → 到点触发 flushSave；
  3. PUT 打到已关闭的测试服务 → NetworkError → handleSaveError → scheduleRetry
     指数退避 → **无限重试循环**，Node 事件循环永不空，进程永不退出。

排除过的方案（都无效）：
  · 服务器加 `Connection: close`  —— undici 连接池仍持有 socket
  · 独立 `undici.Agent` + agent.close() —— 全局 fetch 不走该 Agent
  · `process._getActiveHandles()` 检查 —— 剩余 Socket 是 stdio，不是真因

修复：走 app.js 的**登出分支**（`app.js:496` 的 `syncEngine.destroy()` →
`clearTimers()`），在 finally 中先触发登出再关 server。这条路径本就是为
「退出登录时清掉已排入的防抖定时器」设计的，走真实公开入口，未改动被测源码。

  代价：dirty 用例的语义从「断言后立刻结束」变为「断言 → 登出清理 → 结束」，
  但断言本身仍发生在输入后 30ms，**未放宽**。

这一条也解释了为什么 M5 原交付（无真实 HTTP 驱动的冲突测试）不会遇到此问题：
她的测试不触发真实 PUT，也就没有「PUT 打到已关闭服务」这条路径。
**引入真实驱动的代价是必须自己管理资源生命周期**——这是本轮修复中最值得记住的一点。
