## 四、M1 修复的两处真实缺陷（她上报，M1 定位根因并修）

### F-01 JSON 体 > 2 MiB 返回 400（应 413）

**M1 实测确认**（交件基线原样）：

```
状态: 400
响应体: {"error":{"code":"BAD_REQUEST",
        "message":"JSON payload (2400028 bytes) is larger than allowed (limit: 2097152 bytes)."}}
```

**她的建议不准确**：她说「把 `JsonPayloadError::Overflow` 映射到 413」——但代码里**已经**映射了。

**真正根因**（M1 查 actix-web 4.17 源码确认）：

```rust
pub enum JsonPayloadError {
    OverflowKnownLength { length: usize, limit: usize },  // 带 Content-Length 时触发
    Overflow { limit: usize },                            // 分块传输（无 Content-Length）
    ...
}
```

代码只匹配了 `Overflow`，而浏览器与常规客户端都带 `Content-Length` → 命中 **`OverflowKnownLength`** → 落到 `other => bad_request` → **400**。

**修复**：`routes/mod.rs` 与 `routes/auth.rs` 两处同时匹配两个变体。

**修复后实测**：`413` + `{"code":"PAYLOAD_TOO_LARGE"}` ✅

### F-02 非法 UUID 返回 404 纯文本（应 400 JSON）

**M1 实测确认**：

```
状态: 404
Content-Type: text/plain; charset=utf-8
响应体: UUID parsing failed: invalid character: found `n` at 0
```

**修复**：给 documents 路由挂 `PathConfig::error_handler`，把路径参数解析失败统一映射为 400 JSON。**「资源不存在」仍由 handler 的 `AppError::NotFound` 返回 404**，二者语义分离。

**修复后实测**：`400` + `application/json` + `{"code":"BAD_REQUEST","message":"路径参数无效：…"}` ✅

### 修复不破坏基线

在 `3373a9e` worktree 上应用修复后复跑：**118 passed / 0 failed / 58 ignored，与基线完全一致**。

> **过程记录（M1 自身失误）**：第一次验证时我把 integration 分支的 `routes/mod.rs` **整文件覆盖**到 worktree，导致 lib 测试从 98 掉到 97（两分支该文件有差异）。改回**最小编辑**后恢复 118。**教训：跨分支验证严禁整文件覆盖。**
