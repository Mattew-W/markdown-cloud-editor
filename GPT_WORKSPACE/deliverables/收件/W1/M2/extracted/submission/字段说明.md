# 字段说明

项目：Markdown 云同步编辑器（M2 本周本地练习）
范围：只说明 `users` 和 `documents` 两张表需要存什么，不涉及后端查询、接口或 Rust 数据模型。

> 说明：下表中的类型、长度和默认值均为建议值，最终由 M1 确认后写入正式迁移。

## 1. users 表（用户）

| 字段 | 用途 | 建议类型 | 是否必填 | 补充说明 |
| --- | --- | --- | --- | --- |
| `id` | 用户的唯一标识，作为主键 | `UUID`，默认 `gen_random_uuid()` | 是 | 由数据库生成；也可改为由应用生成，待 M1 确认 |
| `username` | 登录用户名，保存前统一转为小写 | `VARCHAR(32)` | 是 | 全表唯一；只允许小写字母、数字、下划线、短横线，长度 3–32 |
| `password_hash` | 密码的 Argon2id 哈希（PHC 字符串） | `TEXT` | 是 | 只存哈希，禁止存明文，禁止返回给前端 |
| `created_at` | 用户注册时间，统一存 UTC | `TIMESTAMPTZ`，默认 `CURRENT_TIMESTAMP` | 是 | 由数据库生成 |

## 2. documents 表（文档）

| 字段 | 用途 | 建议类型 | 是否必填 | 补充说明 |
| --- | --- | --- | --- | --- |
| `id` | 文档的唯一标识，作为主键 | `UUID`，默认 `gen_random_uuid()` | 是 | 由数据库生成；也可改为由应用生成，待 M1 确认 |
| `owner_id` | 文档所属用户的 `id`，外键指向 `users.id` | `UUID` | 是 | 每篇文档必须有且只有一个所有者；删除用户时默认 `RESTRICT` |
| `title` | 文档标题 | `VARCHAR(255)` | 是 | 去掉首尾空白后长度 1–255 个字符；未提供时由应用填“未命名文档” |
| `content` | Markdown 正文原文 | `TEXT` | 是 | 允许空字符串；UTF-8 编码后不超过 262144 字节（256 KiB） |
| `version` | 保存版本号 | `INTEGER`，默认 `1` | 是 | 必须大于 0；每次成功更新加 1，用于检测并发冲突 |
| `created_at` | 文档创建时间，统一存 UTC | `TIMESTAMPTZ`，默认 `CURRENT_TIMESTAMP` | 是 | 由数据库生成 |
| `updated_at` | 最后一次成功更新时间 | `TIMESTAMPTZ`，默认 `CURRENT_TIMESTAMP` | 是 | 首版由应用的 `UPDATE` 语句显式设置，不使用数据库触发器 |

## 3. 用通俗话解释

- **用户名不能重复**：`username` 上有唯一约束（`UNIQUE`）。数据库里不允许出现两个相同的用户名，注册时重名会失败，应用把它转换成 `USERNAME_TAKEN` 错误（HTTP 409）。
- **每篇文档属于一个用户**：`documents.owner_id` 是指向 `users.id` 的外键。文档不能没有主人，也不能指向一个不存在的用户。查询文档时必须同时限定 `owner_id`，避免读到别人的文档。
- **密码只存哈希**：数据库里保存的是 Argon2id 计算出的 `password_hash`，不是用户输入的密码。登录时把输入密码按同样算法验证；即使数据库内容泄露，也无法直接得到原始密码。
- **`version` 表示保存版本**：新建文档时 `version = 1`。每次成功保存后 `version` 加 1。客户端保存时提交它期望的旧版本 `expected_version`，只有数据库里的版本与它一致才允许更新；不一致说明别人已经改过，返回版本冲突（409），从而避免互相覆盖。

## 5. 两表关联

```text
users (1) ────< (N) documents
          id  ←  owner_id
```

- 一个用户可以拥有多篇文档；一篇文档只属于一个用户。
- `documents.owner_id` 非空，且必须能在 `users.id` 中找到对应记录。
- 首版没有删除账号功能；外键使用 `ON DELETE RESTRICT`，防止误删用户时连带删除文档。

1. `id` 统一用 `UUID DEFAULT gen_random_uuid()`，还是由应用生成 UUID？本机 PostgreSQL 需 13 版以上才内置该函数（项目计划使用 17 系列）。
2. `username` 的小写、字符范围和长度检查是否写入数据库 `CHECK`，还是只在应用层校验？本稿写入了数据库约束作为兜底。
3. `content` 的 256 KiB 上限是否保留为数据库 `CHECK`？每次写入都会计算字节长度，需确认可接受。
4. 标题的 `trim` 在应用中按 Unicode 空白处理；数据库 `CHECK` 使用 `btrim`（只去普通空格），是否需要统一语义？
5. `updated_at` 首版由应用 `UPDATE` 显式赋值，不建触发器；是否确认？
6. 正式迁移文件名是否使用 `0001_init.sql`，是否需要单独的回滚脚本？
7. 是否保留 `(owner_id, updated_at DESC, id DESC)` 复合索引（本稿已加）？
