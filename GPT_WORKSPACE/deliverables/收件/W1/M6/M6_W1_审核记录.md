## 五、与项目规范的差距（决定能否并入）

### 5.1 硬约定差距（§08 / §10）

| 项 | 规范要求 | 当前实现 | 后果 |
|---|---|---|---|
| 草稿键 | 含 `user_id` + `doc_id` + `edit_session_id`（§08:374） | 单一固定键（`drafts.js:1`） | 跨账号草稿互相可见（隐私事故）；多窗口、多文档互相覆盖 |
| 草稿记录 | 含 `base_version`、`title`、`content`、`local_revision`、记录时间（§08:376） | 仅 `{content, savedAt}` | 冲突判定与安全清理均无法实现；**标题改动完全无草稿保护** |
| 模块形态 | ES Modules（§10:412） | 普通脚本，0 个 export | 无法被 `sync.js` 导入 |
| DOM 耦合 | drafts.js 统一管理草稿，DOM 归 editor.js（§05:217） | drafts.js 直接读写 DOM 并绑定事件 | 无法用 Node 内置测试验证；与 M5 的 editor.js 争抢节点 |
| 清理逻辑 | 清理前核对会话、修订号、内容（§08:376） | 直接 `removeItem` + 清空编辑器 | 保存在途时点清除，会抹掉刚产生的新修改——§08:376 明令禁止 |
| 恢复判定 | 三分支（相同／版本同／进 conflict）（§08:378） | 单键直读直写 | 依赖 base_version，当前无从实现 |

### 5.2 语义风险最高的一条

`drafts.js:19` 文案「✅保存成功，保存时间：…」——§08:349 明文「本地备份成功不能显示成云端保存成功」。这行字若原样搬进正式状态栏，用户会误以为内容已上云。**W2 第一条必须纠正。**

### 5.3 同名陷阱（须优先防范）

文件名叫 `drafts.js`，但实现不是规范 §08 的草稿模块。若直接复制进主项目，`sync.js` 调用不了它，M1 只能另写一份真正的草稿逻辑 → 仓库出现**两份语义不同的 `drafts.js`**，正是 §05:217 明令禁止的「不一致副本」。**文件同名 + 职责不符即为此类问题的温床。**

### 5.4 应予肯定

组员严格守住 §12:472 的 M6 职责边界，未越界写 sync 状态机或 E2E，未碰后端；全程 `innerText`，未用 `innerHTML`；未存任何密码 token；存储键用 demo 专用命名，与正式前缀无实际冲突。

### 7.1 需先冻结的前置契约（缺一项 M6 必然二次返工）

| # | 契约 | 要点 |

| C1 | 草稿记录 Schema | `{user_id, doc_id, edit_session_id, base_version, title, content, local_revision, recorded_at}`；`recorded_at` 用 ISO 8601 UTC，不用 `Date.now()` 数字 |

| C6 | 错误类型 | `DraftStorageError{reason:'quota'\|'unavailable'\|'corrupt'\|'serialize'}`；**禁止把 `e.message` 直接透出** |

| C9 | 草稿与保存状态机关系 | 草稿是兜底，自动保存是主路径；**草稿写入成功不得改变 synced/dirty 判定** |
