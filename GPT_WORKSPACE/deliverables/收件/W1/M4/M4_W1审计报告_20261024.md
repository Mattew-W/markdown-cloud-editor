### 3.2 与主仓库既有实现的接口漂移（合入成本）

| 项 | 主仓库（M1，未提交） | M4 W1 | 漂移影响 |
| --- | --- | --- | --- |
| 更新确认响应类型名 | `UpdateDocumentResponse` | `DocumentUpdateConfirmResponse` | 同名不同物，`dto/mod.rs` 二选一 |
| 时间戳序列化 | `String`，`format_timestamp()` 秒级 RFC 3339（`…Z`） | `DateTime<Utc>`，serde 直出**亚秒级可变精度** | 响应体精度不一致，既有断言/前端展示受影响 |
| 删除查询 DTO | `DeleteDocumentQuery { expected_version }` | **缺失**（service 直接收 i32） | HTTP 层缺 Query 提取结构 |
| 错误模型 | `AppError` + `ErrorCode`（`as_str()` 产出稳定字面量） | `DocumentServiceError`（无 code） | 需另写映射层 |
| Service 形态 | 自由函数 + `&PgPool` | 泛型 `DocumentService<R>` + trait | 两套范式并存 |
| DTO 派生 | `Debug, Clone, Serialize, Deserialize` | 仅 `Debug, Serialize`（缺 Clone/Deserialize） | 编译期灵活性差异 |
| thiserror | v2 | v1 | 依赖版本分叉 |

> 两类实现**同名类型完全相同**（`CreateDocumentRequest` 等 6 个）。合入不是复制文件，必须先删其一，否则 `dto/mod.rs` glob 再导出即二义性编译错误。

### 3.3 代码级发现（独立于契约）

- **F5（P1）413 语义错误 + 死代码**：`DocumentServiceError::PayloadTooLarge`（注释标注"正文超限 → 413"）与 `Internal` **在全 crate 内从未被构造**（已全文检索证实）。正文超限实际走 400。
- **F6（P1）update 路径不归一化标题**：`update_document` 调 `req.validate()?`（只校验、不返回 trim 结果），随后把**原始 `req.title`**（含首尾空白）传给 repository；而 create 路径 trim 后传入。同一份数据经两条路径落库形态不一致，也与主仓库 `validate_title()` 返回 trim 值的实现不一致。
- **F7（P2）trait 被迫二次读库**：`DocumentRepository::update` 返回 `Option<DocumentUpdateResult>`，**结构上无法回传 `server_version`**，service 只能在失败后再 `get_by_id` 一次区分 404/409。该模式与主仓库 repo 层 probe 思路相同（TOCTOU 窗口同样存在、影响同等有限），但 M4 把它下沉到了 service 层，且每次冲突多一次往返。
- **F9（P2）仓储 trait 的错误类型倒置不彻底**：`DocumentRepository` 的返回错误是 `DocumentServiceError`（服务层枚举），数据层实现无法区分"连接失败/约束违反/超时"，只能一律冒充 `Internal`。
- 非测试代码无 `unwrap/expect/panic!/unsafe`；无密钥、连接串、日志打印——此项干净。
