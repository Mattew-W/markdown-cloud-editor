## 四、核心架构要点

### 1. 越权访问统一返回 404（而非 403）
- **安全依据**：若文档存在但属于其他用户时返回 403，未授权攻击者就可以通过遍历 UUID（或彩虹表探测）枚举系统中存在哪些文档 ID，从而泄露系统资源的存在性元数据。统一返回 404，攻击者无法区分“此文档不存在”还是“该文档属于别人”。
- **分层落地**：所有 SQL 查询在 `WHERE` 条件中无条件绑定 `owner_id = $`，在数据库引擎层直接实现租户物理隔离。

### 2. 单条带版本条件的原子 SQL 杜绝丢失更新
- **痛点**：若采用应用层“先 SELECT 读版本，再 UPDATE 写数据”，在高频自动保存或多标签页编辑场景下，两个并发请求在 SELECT 和 UPDATE 之间存在时间窗口，后写入的会直接覆盖先写入的数据，且双方都不报错（静默丢数据）。
- **解法**：
  ```sql
  UPDATE documents 
     SET title = $1, content_markdown = $2, version = version + 1, updated_at = CURRENT_TIMESTAMP
   WHERE id = $3 AND owner_id = $4 AND version = $5
  ```
  单条 SQL 在数据库事务和行锁粒度上完成原子版本校验与递增。如果受影响行数为 0，再通过极轻量的单条验证判断是版本冲突（409 并提取 `server_version`）还是文档不存在（404）。

### 3. PUT 整体替换语义
- 严格遵循 REST 规范，PUT 是整体替换而非 PATCH。客户端必须全量提交 `title`、`content` 与 `expected_version`。更新成功后仅返回轻量的 `{id, version, updated_at}`，不重复回传可能高达 256KB 的 Markdown 正文，显著减少网络往返消耗。

### 4. 独立 Schema 隔离并发测试
- `cargo test` 默认多线程并发执行。如果共用公共表并用 `TRUNCATE` 清理，会导致线程间相互破坏数据。本套测试为每个测试用例分配一个专属的隔离 Schema（`t_<thread>_<seq>_<timestamp>`），各自建表跑测，运行完毕集中清理，做到了 100% 隔离与并行安全。

## 五、四道核心理解题精解（供本人答辩与把关）

> 本节针对交付说明中的 4 道答辩理解题提供深度技术梳理，供 M1 黄昊本人复核并掌握关键设计逻辑：

#### Q1: 为什么越权访问返回 404 而不是 403？
- **核心要点**：
  1. **防止资源枚举（Resource Enumeration）**：403 Forbidden 意味着“我知道你要访问什么，但我拒绝你访问”；404 Not Found 意味着“在这个空间里找不到该资源”。如果对他人文档返回 403，任何合法登录的用户都可以通过遍历探测确定哪些 UUID 对应的文档是存在的，造成敏感元数据泄漏。
  2. **契约规定**：规范 §06 明确要求：资源属于租户私有空间，未授权访问统一按“不存在”处理。

#### Q2: 为什么更新必须是「单条带版本条件的 SQL」，而不能先 SELECT 再 UPDATE？
- **核心要点**：
  1. **避免竞态条件（Race Condition）**：在 Web 环境中，前端定时自动保存（如 2 秒一次）与用户手动保存极易并发。若先 SELECT 得到 version=1，在准备 UPDATE 之前另一个请求已经完成写入将 version 变为 2；此时如果不带 `version = 1` 条件直接 UPDATE，就会以旧正文强行覆盖新正文，发生**静默数据丢失（Silent Data Loss）**。
  2. **利用数据库行级锁原子性**：带 `WHERE id=$1 AND owner_id=$2 AND version=$3` 的单条 UPDATE 语句会在引擎层加行排他锁，只有版本完全匹配时才生效，不给并发竞态留下时间窗口。

#### Q3: PUT 是整体替换而不是 PATCH，这意味着什么？客户端要注意什么？
- **核心要点**：
  1. **语义不同**：PUT 代表幂等的完整资源替换，未提供的字段不能保留原值（或者按契约直接 400 拒绝）；PATCH 才是局部更新。
  2. **客户端注意事项**：调用 PUT 时必须持有文档的完整副本（含最新 title 和 content），绝不能只传递修改的局部片段；必须随带上次读取到的 `expected_version`；如果更新遭遇 409，必须获取最新的 `server_version` 和最新内容执行三路合并（3-way merge）或提示用户覆盖。

#### Q4: 测试为什么每个用例建独立 schema，而不是共用一张表后 TRUNCATE？
- **核心要点**：
  1. **并发安全（Thread Safety）**：Rust 的 `cargo test` 默认在多线程线程池中并行执行测试。如果多个测试同时向同一张表插入、查询和 `TRUNCATE`，会出现不可预期的死锁、脏读和用例偶发失败（Flaky Tests）。
  2. **环境纯净与可重现**：每个测试在形如 `SET search_path TO t_xxx` 的独立命名空间内运行，数据生命周期与测试线程严格绑定，测试失败时方便精准保留現場，测试结束后运行一键脚本集中删除，既快速又干净。
