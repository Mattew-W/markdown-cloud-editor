## 1. 起点状态（复核发现）

接手时工作树中已存在 M1 自己写的 R1/R2/R3 骨架（未提交），但 `npm test` **3 个用例失败**：

| 失败用例 | 现象 |
| --- | --- |
| 返回 JSON 响应头 + 不完整正文后断开连接 → NetworkError | `AssertionError: expected true, actual false`（`headersArrived` 未置位） |
| 成功（200）正文读取超时 → TimeoutError | `error: '网络请求失败'`（归入 NetworkError 而非 TimeoutError） |
| 错误（400）正文读取超时 → TimeoutError | 同上 |

**根因（捕获顺序 bug）**：`makeFetchNotifyOnHeaders(fetchImpl, …)` 在 `await start()` **之前**调用，
闭包捕获了 `fetchImpl` 的**旧值**（首次为 `undefined`，其后为上一轮测试的已关闭端口），
导致三个用例全部把请求打到错误的服务端。

**次生根因**：`makeTimers` 的 `clearTimeout` 只记录不取消，
使得「超时保护提前结束」这类变异在假时钟下毫无影响 → 用例会误判为通过。

## 2. 修复内容

### 2.1 惰性取值修掉捕获顺序 bug（R1/R2 共同前置）
`makeFetchNotifyOnHeaders` 的第一个参数由**函数值**改为**取值函数** `getBaseFetch`：

```js
function makeFetchNotifyOnHeaders(getBaseFetch, onHeadersSettled, onBodyRead) {
  return async (url, init) => {
    const baseFetch = getBaseFetch();   // ← 调用时才取值
    …
  };
}
```

三处调用点改为 `() => fetchImpl`。附带注释说明「若直接传函数值，闭包会捕获上一次测试的旧端口」。

### 2.2 假定时器补齐真实 `clearTimeout` 语义
`makeTimers` 增加 `cancelled: Set`，`clearTimeout(id)` 真正标记该定时器失效；
`trigger()` 返回布尔值——`true` = 定时器仍有效并已触发，`false` = 已被清除（未触发）。

### 2.3 补「场景前提自证」断言（M6-R14 的落地）
新增 `onBodyRead` 回调：包装 `response.json()`，在**正文读取真正开始**时置位。
两个超时用例改为 `await bodyRead`（promise 等待）后再断言，
并断言 `state.trigger() === true`（超时定时器必须仍然有效）。

> 注：初版用 `assert.equal(bodyReadStarted, true)` 即时断言会**误报失败**——
> `await started` 恢复时 api.js 尚未走到 `response.json()`（时序竞态）。
> 改为 promise 等待后既消除竞态，也确保断言的是「确实已发生」而非「恰好为真」。

### 2.4 补 409 VERSION_CONFLICT 用例（R3）
- 携带 `server_version: 7` → `VersionConflictError`，断言 `serverVersion === 7`、两种 409 不混淆、`requestId` 保留
- 缺 `server_version` → `ProtocolError`，不编造版本号

### 2.5 补九类 error.code 真实传输映射 + DELETE 查询参数用例
- 契约 API.md §4.1 的九个字面量在真实 HTTP 传输下逐类验证
- `DELETE /documents/u1?expected_version=3` → 204 返回 `null`，版本号在查询串而非请求体

### 3.1 M2 变异的设计修正（方法论要点）

初版 M2 变异是「粗粒度」的（改错误分类分支），它**连带破坏了 5 个不相关用例**——
检出是"真的"，但无法证明检出点就是目标机制。

改为**阶段定向变异**后（只在 `fetch` 返回后清定时器，其余逻辑不动），
初版用例**漏检**（退出码 0、全部通过）。这暴露了初版用例的真实缺陷：
它**无法区分**「超时保护覆盖正文读取」与「只覆盖 fetch 阶段」。

补上 §2.2 + §2.3 两项断言后，M2 精确检出，且只失败目标用例。

> 这正是 11-04 工作日志记录的教训：「M1 自己做变异测试时用的是粗粒度变异，能检出；
> 但缺少只改某一阶段行为的定向变异，导致漏掉场景层问题。」
> 本次是同一教训的**自我验证**——定向变异确实抓出了自己写的用例的缺陷。
