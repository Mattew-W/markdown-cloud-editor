## 四、覆盖缺口（M1 变异测试发现）

我做了**变异测试**检验 12 个用例的鉴别力——把 `api.js` 改成各种错误实现，看测试能否检出：

| 变异 | 结果 |
|---|---|
| M1 URL 改回 `dummy-base` 绝对 URL | ✅ 检出（6 个用例失败） |
| M2 204 也调用 `response.json()` | ✅ 检出 |
| M3 移除 AbortError → TimeoutError 分类 | ✅ 检出 |
| M4 移除 finally 的定时器清理 | ✅ 检出 |
| M5 令牌不放 header | ✅ 检出 |
| **M6 移除 Content-Type 检查** | ❌ **未检出** |
| M7 所有错误都归 ApiError | ✅ 检出 |

### 缺口详情

**M6 未检出的原因**：12 个真实传输用例中**没有「服务端返回 `text/html` 错误页」这一场景**。

任务书原文要求：「非JSON返回ApiError保留status、不读HTML作JSON」——这一条只被 `api.test.js`（M1 代修时新增的 mock 版）覆盖，属于**沿用覆盖**，不是 W3 的新增覆盖。

**实测差异**（真实服务返回 `<html>...`）：

| 实现 | 错误类型 | message | 暴露 HTML |
|---|---|---|---|
| 原始实现（正确） | `ApiError` | 接口返回状态码 500 | 否 |
| M6 变异后 | `ProtocolError` | 错误响应内容不是合法 JSON | 否 |

两者行为**确实不同**，但真实传输测试抓不到。

### M1 已补

在 `api.http.test.js` 中补 1 个用例（`ApiError` 已加入 import）：

```js
test('非 JSON 错误响应（text/html 错误页）→ ApiError，保留 status，不把 HTML 当 JSON 解析', ...)
```

**补后验证**：13/13 通过；**M6 变异现在被精确检出**（第 11 项失败），此前为 0 检出。

## 五、另一处发现：主项目落后于 W3 基线

比对主项目 `frontend/js/api.js`（10-26 W2 代修版）与 W3 基线（11-01，提交 `42e9e7f`）：

| 版本 | `response.json()` catch 块 |
|---|---|
| 主项目（10-26） | `catch {` |
| W3 基线（11-01） | `catch (error) { if (!(error instanceof SyntaxError)) throw error; }` |

**基线版多两处 `SyntaxError` 判别**。这正是任务书提到的「审查又修复响应正文读取超时和网络中断的错误分类」。

**我实测了该判别的实际效果**：

| 场景 | 基线版（含判别） | 主项目版（去判别） |
|---|---|---|
| 正文不完整 + 断连 | `NetworkError` | `NetworkError`（**相同**） |
| 正文完整但 JSON 语法错 | `ProtocolError` | `ProtocolError`（**相同**） |

**结论：在 Node 22.23 的 undici 下，这处判别从未被触发**——断连时 undici 抛的是 `TypeError: fetch failed` 而非 `SyntaxError`。它是一处**防御性冗余代码**，无害但当前无实际作用。

**已把基线版同步进主项目**（含这处加固），保持与冻结基线一致。
