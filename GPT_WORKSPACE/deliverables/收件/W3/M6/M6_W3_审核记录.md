## 五、另一处发现：主项目落后于 W3 基线

比对主项目 `frontend/js/api.js`（10-26 W2 代修版）与 W3 基线（11-01，提交 `42e9e7f`）：

| 版本 | `response.json()` catch 块 |
|---|---|
| 主项目（10-26） | `catch {` |
| W3 基线（11-01） | `catch (error) { if (!(error instanceof SyntaxError)) throw error; }` |

**基线版多两处 `SyntaxError` 判别**。这正是任务书提到的「审查又修复响应正文读取超时和网络中断的错误分类」。

**我实测了该判别在三种场景下的实际效果**：

| 场景 | 基线版（含判别） | 主项目版（去判别） |
|---|---|---|
| A 正文优雅截断（`Content-Length` 声明长于实际，连接正常结束） | `NetworkError` | `ProtocolError`（**不同**） |
| B 正文完整但 JSON 语法错 | `ProtocolError` | `ProtocolError`（相同） |
| C 断连（socket 被销毁） | `NetworkError` | `NetworkError`（相同） |

**修正**：本记录初稿写的是「这处判别**从未被触发**」——**该措辞过于绝对**。准确表述是：

> **这处判别在场景 A（正文被优雅截断但连接正常结束）时确实会生效**：
> undici 抛 `SyntaxError: Unexpected end of JSON input`，判别将其原样重抛，
> 最终归 `NetworkError`（而非就地转成 `ProtocolError`）。
> **只在断连场景（场景 C）不触发**——此时 undici 抛的是 `TypeError: fetch failed`。

**结论修正**：这处加固**有实际作用**，修的是「正文不完整被误判为协议错误」；并非防御性冗余。**已把基线版同步进主项目**（含这处加固），保持与冻结基线一致。

> 附带的脆弱性（记录，非缺陷）：`api.js:353` 依赖 `error.name === 'AbortError'` 而非 `error.cause?.name`。若某运行时改抛 `TypeError: fetch failed (cause: DOMException AbortError)`，分类会退化为 `NetworkError`。当前 Node 22.23 的 undici 实测三种 abort 时机**均为 `DOMException/AbortError`**（`cause` 为 `undefined`），现状正确。

## 五之二、返工必修项（**已完成**，2026-11-05）

> 以下三项是**场景层缺口**，与 §四 M1 的 Content-Type 缺口同类。**M1 已全部完成并合入主项目**。

| # | 必修项 | 完成情况 | 验收（变异测试） |
|---|---|---|---|
| **R1** | 让断连用例的**响应头真正送达**客户端 | ✅ 已完成 | 把「延迟 30ms destroy」改回「立即 destroy」→ **用例失败**（检出） |
| **R2** | 让超时用例**真正进入正文读取阶段** | ✅ 已完成 | 注入「正文读取阶段的 abort 改归 NetworkError」→ **用例失败**（检出） |
| **R3** | 补齐 `VERSION_CONFLICT`(409) 的 `serverVersion` 真实传输用例 | ✅ 已完成 | 注入「VERSION_CONFLICT 编造 serverVersion」→ **用例失败**（检出） |

### R1 的实现与一个实测发现

实现采用 `flushHeaders()` + **延迟 30ms** `destroy()`，并新增 `headersArrived` 断言（客户端必须先收到响应头）。

**实测四种组合**（每种独立观察 `fetch` 是否 resolve）：

| 组合 | 客户端拿到响应头 | fetch resolve |
|---|---|---|
| flushHeaders + **立即** destroy | ❌ 否 | false |
| flushHeaders + **延迟 30ms** destroy | ✅ 是 | true |
| 无 flushHeaders + **立即** destroy | ❌ 否 | false |
| 无 flushHeaders + **延迟 30ms** destroy | ✅ 是 | true |

**结论：决定因素是「延迟」而非 `flushHeaders`**——`flushHeaders()` 只保证数据写进 socket，不保证出网；延迟 30ms 才让响应头真正抵达客户端。

### R2 的实现

新增 `makeFetchNotifyOnHeaders(getBaseFetch, onHeadersSettled, onBodyRead)`：

- **惰性取值**：`getBaseFetch` 传函数而非函数值。`fetchImpl` 在 `start()` 里被重新赋值，若直接传函数值会捕获上一次测试的旧端口。
- **`onBodyRead` 钩子**：包装 `response.json()`，被调用时 resolve `bodyRead` promise。测试 `await bodyRead` 后才触发超时——**这就是「已进入正文读取阶段」的自证**。

同时 `makeTimers` 改为**真正取消**定时器（`cancelled: Set`），`trigger()` 返回布尔值表示该定时器是否仍有效。这修复了「超时保护提前结束」类变异在假时钟下毫无影响的问题。

### R3 与错误码补齐

新增 4 个用例：

| 用例 | 覆盖 |
|---|---|
| 九类 `error.code` 全部映射 | 真实传输下 8 类（含 401/413/503，此前只测 400/404/500/429）+ 409 单独测 |
| `409 VERSION_CONFLICT` 携带 `serverVersion` | 断言 `instanceof VersionConflictError`、**不** `instanceof ConflictError`、`serverVersion === 7`、`requestId` |
| `409 VERSION_CONFLICT` 缺 `server_version` | 归 `ProtocolError`，不编造版本 |
| `DELETE` 的 `expected_version` 走**查询参数** | 契约 `API.md` §3.6；断言服务端实收 `req.url` 含 `expected_version=3` |

**真实传输层用例数：12 → 17。**

### 排查过程中发现并修正的一处工作区污染

改造初期测试出现挂起（第 11 项后输出中断）。定位过程：

1. 插桩显示 `json:start` 事件出现、`catch(AbortError)` 出现，但最终分类是 `NetworkError`——矛盾

### 四.2「分块断连 → NetworkError」：响应头从未送达客户端

**交件写法**（`api.http.test.js:219-227`）：

```js

res.write('{"partial":');

```

**M1 独立复现**（20 次）：

```
20 次中客户端拿到响应头的次数: 0/20
→ 断言1「响应头未送达」: 成立
```

`res.destroy()` 立即销毁 socket，**TCP 缓冲区里的响应头随 socket 一起被丢弃**。服务端"写出了响应头"≠"客户端收到了响应头"。

**任务书原文要求「先返回 JSON 响应头和不完整正文再断开连接」——此前提不成立。** 实际测的是"连接被重置"，而非"分块响应中途断开"。

**鉴别力**：把 api.js 改成「删掉 AbortError 分支、所有错误一律归 NetworkError」，**该用例仍然通过**——因为错误发生在 fetch 阶段（`api.js:267`），`response.json()` 根本没被调用。

**正确的写法**（已验证可检出）：`res.flushHeaders()` 后延迟 30ms 再 `res.destroy()`，响应头就能送达客户端。

### 四.3「正文读取超时 → TimeoutError」：`json()` 从未被调用

**M1 独立复现**（对 api.js 副本插桩，记录 `fetch:start` / `fetch:resolved` / `json:start` / `catch` 四个阶段）：

```
status 200:
  trigger 前事件: []
  全部事件    : ["catch:AbortError"]
  json() 被调用: 否
status 400:
  trigger 前事件: []
  全部事件    : ["catch:AbortError"]
  json() 被调用: 否
```

**abort 发生在 `await fetchImpl(...)` 期间，响应头尚未送达，`response.json()` 根本没被调用。**

交件的服务端在 `writeHead` 后立即 `startedResolve()`（`:237`/`:256`），测试随即触发超时——**测试等的是"响应头到达"，不是"正文读取"**。

**这意味着任务书第 7、8 条验收点声称覆盖的「正文读取阶段超时」语义，两个用例实际都没测到。**

**鉴别力**：构造只让「已进入正文读取阶段」的 abort 改归 `NetworkError` 的变异，**这 12 个用例 100% 漏检**；而 mock 版 `api.test.js` 检出 2 项失败（正是 200/400 响应体读取超时两个用例）。

### 四.4 这两处该怎么定性

| 项 | 判定 | 说明 |
|---|---|---|
| 用例是否**真实** | ✅ **真实** | 真 `node:http`、真 socket、真 undici fetch，服务端实收 `req.url`/header/body 并据此断言 |
| 用例是否**有效** | ⚠️ **部分有效** | 覆盖了 mock 版无法覆盖的 9 个维度；但两个被点名的验收点测的不是声称的场景 |
| 用例是否**假测试** | ❌ **不是** | 断言都基于真实服务端行为，无 `assert.ok(true)` 式凑数 |
| 结论 | **真材实料，但存在"看起来通过而实际没测到"的部分** | 与 M1 独立变异测试的结论一致（§四 M6 缺口是同一性质的问题） |

**这正是"Mock 不得访问真实后端"条款想防的问题的另一面**：真实传输测试确实比 mock 强，但它也需要**变异测试**来验证自己的鉴别力。W3 做到了真实传输这一层，尚未做到"验证测试本身"这一层。
