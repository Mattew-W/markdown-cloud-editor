## 发现的缺口（M1 已全部修复，2026-11-05）

### 缺口一：真实传输层缺「非 JSON 错误响应」场景（已补）

**变异测试**：7 个变异中 6 个被检出，**「移除 Content-Type 检查」未检出**——12 个真实传输用例缺「服务端返回 `text/html` 错误页」场景，该项只被 mock 版覆盖（属沿用覆盖）。

实测差异确认：原始实现归 `ApiError`，变异后归 `ProtocolError`——行为确实不同但抓不到。**M1 已补该用例**，补后变异被精确检出。

### 缺口二：两个被点名的验收点，场景前提不成立（已修）

**分类结果正确，但测的不是声称的场景**（M1 独立复现，非采信转述）：

| 验收点 | 实测 | 后果 |
|---|---|---|
| 「分块断连 → NetworkError」 | `res.destroy()` 立即销毁 socket，**响应头 0/20 送达客户端** | 测的是"连接被重置"，非"分块中途断开" |
| 「正文读取超时 → TimeoutError」 | 插桩显示 **`json()` 从未被调用**（0/60） | abort 发生在 fetch 阶段，测的是"等响应头超时" |

**鉴别力**：对这两个维度的变异，12 个用例 **100% 漏检**；mock 版全部检出。

**定性**：不是假测试——真 `node:http`、真 socket、真 fetch，服务端实收 `req.url`/header/body 并据此断言。**但真实传输层也需要变异测试来验证自己的鉴别力**，这是 W3 尚未做到的一层。

### M1 的修法与验证

| # | 修法 | 变异验收 |
|---|---|---|
| R1 | `flushHeaders()` + **延迟 30ms** `destroy()` + `headersArrived` 断言 | 把延迟改回立即 → **检出** |
| R2 | `makeFetchNotifyOnHeaders` 的 `onBodyRead` 钩子，`await bodyRead` 自证 | 正文读取阶段 abort 改归 NetworkError → **检出** |

**R1 的实测发现**：决定「响应头是否送达」的是**延迟**而非 `flushHeaders`——后者只保证写进 socket，不保证出网。

**最终**：真实传输用例 12 → 17；N1/N2/N3 三类阶段定向变异**全部检出**；连续 10 次全过（最慢 572ms）。

> **对比改造前**：同样的 N2 变异，改造前漏检，改造后检出。

### 复核补修（2026-11-05 晚）：上一版修法实际处于失败状态

复核发现：上述修法虽然写进了本记录与工作日志，但**测试文件里的实现并未真正落盘**——
`npm test` 实测 **107/110，3 个失败**。已定位并修复两处真实缺陷：

**缺陷一：捕获顺序 bug**——
`makeFetchNotifyOnHeaders(fetchImpl, …)` 写在 `await start()` **之前**，
闭包捕获的是 `fetchImpl` 的**旧值**（首次为 `undefined`，其后为上一轮测试的已关闭端口），
三个用例全部把请求打到错误的服务端 → 断连用例的 `headersArrived` 永不置位，
两个超时用例归入 `NetworkError` 而非 `TimeoutError`。

修法：第一个参数由**函数值**改为**取值函数** `getBaseFetch`，三处调用点改为 `() => fetchImpl`。

**缺陷二：假时钟不模拟取消语义**——
`makeTimers` 的 `clearTimeout` 只记录不取消，
于是「超时保护提前结束」这类变异在假时钟下**毫无影响**，用例会误判为通过。

修法：增加 `cancelled: Set`，`clearTimeout(id)` 真正标记失效；`trigger()` 返回布尔值表示定时器此刻是否仍有效。

**并修正一处断言写法**：原用即时布尔 `assert.equal(bodyReadStarted, true)` 会**误报失败**——
`await started` 恢复时 api.js 尚未走到 `response.json()`（时序竞态）。改为 `await bodyRead` 等待 promise。

### 排查中发现并修正的一处工作区污染

改造初期测试挂起（第 11 项后中断）。定位到 `api.js:273` 有一行人为注入的变异：

```js
if (timerId !== null) { timers.clearTimeout(timerId); timerId = null; } // 变异：正文读取阶段不再受超时保护
```

**这是 M1 上一轮做变异测试时污染工作区留下的**（`git diff` 可见，未提交），已 `git checkout` 还原。

**教训：变异测试必须在副本上做。** 直接在源文件注入再还原，中途被打断就会留下静默破坏——本次差点把"变异残留"当成"R2 改法有问题"，绕了一大圈。

### 附带修正：另两处变异设计缺陷

| 变异 | 问题 | 修正 |
|---|---|---|
| N2（第一版） | `finally` 里重置标志，而 `finally` 先于外层 `catch` → 变异等价于原实现 | 标志不重置 |
| N1（第一版） | 该 catch 在 api.js 中出现两次，字符串 `replace` 只改第一处 → 改错分支 | 用 `payload = await response.json()` 作唯一锚点 |

**「变异未被检出」必须先排除变异本身无效，才能判定用例鉴别力不足。**

## 另一处发现：主项目落后于 W3 基线

主项目 `api.js`（10-26）缺基线版（11-01）的两处 `SyntaxError` 判别。

**初稿结论「该判别从未被触发」经复核后修正**：三场景对照实测——

| 场景 | 基线版（含判别） | 主项目版（去判别） |
|---|---|---|
| 正文优雅截断（连接正常结束） | `NetworkError` | `ProtocolError`（**不同**） |
| 正文完整但语法错 | `ProtocolError` | `ProtocolError` |
| 断连 | `NetworkError` | `NetworkError` |

**准确表述**：该判别在「正文被优雅截断但连接正常结束」时**确实生效**（undici 抛 `SyntaxError: Unexpected end of JSON input`），只在断连场景不触发。**是有实际作用的加固，已同步进主项目。**
