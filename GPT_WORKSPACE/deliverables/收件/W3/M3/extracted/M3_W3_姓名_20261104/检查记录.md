## 4. 修复前证据（1）：纯空白 `sub` 能通过验签

- **动作**：`cargo test --locked --lib 纯空白sub被拒绝`（改动前）
- **输出**：`sub=" " 应被拒绝，实际解析出 " "`；`test result: FAILED. 0 passed; 1 failed`；`exit_code` 非 0（`日志/05_修复前_空白sub用例.txt`）
- **断言**：缺陷成立——`sub` 只做了 `is_empty()` 判空，纯空白串能拿到一份 `Ok(Claims)`，而这些 token 到下游按 `sub` 查用户必然查不到（与 W2 修的「空 sub」同类，只是没覆盖空白）。

## 5. 修复前证据（2）：超大哈希参数把进程直接打死

- **动作**：`cargo test --locked --lib 损坏格式与不兼容参数都不得归类为密码不匹配`（改动前）
- **输出**：`memory allocation of 4398046507008 bytes failed`；进程以 `0xC0000409`（`STATUS_STACK_BUFFER_OVERRUN`）终止，`exit_code=-1073740791`（`日志/06_修复前_参数OOM用例.txt`）
- **断言**：缺陷成立且比「分类错误」更严重——一条 `m=4294967295` 的损坏记录（≈4.4 TB 内存）不是返回 `IncompatibleParams`，而是**整个进程 abort**；`INTERFACES.md` §1.3 要求这类记录映射 500，abort 连 500 都返回不了，且同一进程内的其他请求一起死。

## 11. 已知局限与观察项（不假装解决）

1. **版本标签被篡改的哈希无法与「密码输错」区分**：真实 `v19` 哈希把标签改成 `v16` 后，校验按 `v16` 重算得到不同摘要 → `PasswordMismatch`。这类「记录被改过」在密码学上没有额外校验位可查，只能记录（用例 P4）。它不是「不兼容参数分类」的漏洞，因为参数本身合法。
2. **`TokenError::NotYetValid` 当前不可达**：`Claims` 没有 `nbf` 字段，`decode_token` 也未开启 `validate_nbf`，实测把 `nbf` 放到未来仍能验签通过（探针输出见 `日志/08_观察项_nbf与未来iat.txt`）。`API.md` §7 只要求校验 `exp`/`sub`/`iss`/`aud`，加 `nbf` 校验属行为变更，留给 M1 决定，本次不动。
3. **`exp == now` 在同一秒内仍有效**：`jsonwebtoken` 的比较是「严格小于才过期」，`leeway = 0`。因此 `ttl = 0` 的 token 当秒有效（T8 记录该行为）；生产中 TTL 下限由 `config.rs` 的 `MIN_JWT_TTL_SECS = 60`、上限 `MAX_JWT_TTL_SECS = 86_400` 兜住，`ttl=0` 不会从接口进来。
4. **`ensure_verifiable` 的三个上限是防御性阈值，不是契约值**（1 GiB / 64 次 / 并行 8）。生产参数是 `m=19456 KiB, t=2, p=1`，与阈值相差 50–1000 倍；若将来 deliberately 调重参数，需要同步调这三个常量（若要外置到 `config.rs`，属 M1 接线工作）。
5. **`checked_add_signed` 这一闸的边界**（供本人作答时参考，不是替本人答题）：`TimeDelta` 上限是 `9_223_372_036_854_775` 秒（内部按毫秒存），而 `Utc` 上限约公元 262143 年（距今约 8.2×10¹² 秒）。所以 `i64::MAX` 秒**在 `Duration::try_seconds` 阶段就被拒**，根本走不到 `checked_add_signed`；这正是「不能只依赖 `checked_add_signed`」的原因（见 T9 三档）。
